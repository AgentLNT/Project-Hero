# GAS 框架选型调研

日期：2026-10-21。状态：调研保留备查，当前阶段延期接入 GAS / Flexi；尚未安装依赖或完成接入验证。

最新决定：用户明确当前阶段没有引入复杂技能的打算，魔法尚未实现。此前的 [Flexi 试接入与技能制作方案 v0.1](Flexi试接入与技能制作方案-v0.1-2026-10-21.md)已延期；当前优先改善现有动作的配置与制作流程。本调研保留为后续评估材料，候选比较不代表接入验收。

目标：降低后续技能、效果与被动联动的制作成本，复用已有框架的实际代码和编辑工具。

## 结论

当前不安排框架接入。后续若真实技能需求出现较多效果组合、持续状态、条件触发或跨技能联动，再比较框架与现有配置方式的制作及维护成本；是否加入魔法不是唯一判断条件。

此前候选顺序是 **Flexi** 优先验证、**AbilityKit** 作为模块复用备选、**EX-GAS** 作为 GAS 模型及编辑工作流对照。该顺序仅供重新启动评估时参考，并非当前实施安排或框架通用质量排名。

现有证据不足以认定任何候选可以直接替换当前技能运行时。选型需要同时衡量：能省下多少配置、编辑器和通用逻辑工作，以及需要承担多少适配、版本跟随和回归成本。

## 项目现状与接入条件

本次读取了当前源码，关键事实如下：

| 现状 | 对选型的影响 | 本地依据 |
|---|---|---|
| Unity 6000.6.2f1 | 要验证该具体版本的导入、编辑器与 Player 兼容性 | [ProjectVersion.txt](../../ProjectSettings/ProjectVersion.txt) |
| Logic 程序集设置 `noEngineReferences: true` | 框架运行时若依赖 MonoBehaviour、ScriptableObject，需要拆分或留在编制边界 | [Logic.asmdef](../../Assets/Scripts/Logic/ProjectHero.Logic.asmdef) |
| 已有不可变动作定义、动作计划、单位轨道和整数 Tick 模拟 | 外部技能流程需要接入现有排程、资源事务与固定结算阶段 | [ActionSpec](../../Assets/Scripts/Logic/Actions/ActionSpec.cs)、[BattleSimulation](../../Assets/Scripts/Logic/Simulation/BattleSimulation.cs) |
| ActionType 有 Cast、Item 枚举值，但定义类型匹配目前只接纳 Attack、Guard、Move、Block、Dodge | 枚举预留不等于已具备通用施法与道具制作能力 | [类型匹配校验](../../Assets/Scripts/Logic/Actions/ActionDefinitionValidation.cs) |
| 已有 BuffSystem、效果实例 ID、到期顺序和计时伤害载荷 | 可扩展既有生命周期；引入框架时必须明确效果状态由谁拥有 | [BuffSystem](../../Assets/Scripts/Logic/Status/BuffSystem.cs)、[效果载荷](../../Assets/Scripts/Logic/Status/StatusEffectSpec.cs) |
| 主战斗构建器目前创建空效果目录 | 效果内核与可供批量制作的配置链之间仍有缺口 | [BattleDefinitionBuilder](../../Assets/Scripts/Authoring/BattleDefinitionBuilder.cs) |

由此判断，当前最需要补强的是技能内容表达与配置工具、可组合的效果/属性修改、标签条件和事件触发。已有排程、反应、伤害与回放规则是接入条件。不能仅以框架能展示“火球术”判断适配程度。

## 候选比较

| 项目 | 已核实的能力与状态 | 本项目建议 |
|---|---|---|
| [Flexi](https://github.com/PhysaliaStudio/Flexi) | MIT；提供节点技能编辑、属性修改和运行器；作者标记仍在开发 | **优先验证**，重点考察内容编排与自定义节点复用 |
| [AbilityKit](https://github.com/HOBOBO/AbilityKit) | MIT；提供模块化技能管线、触发与战斗工具；文档强调纯 C# 分层，也明确 API 和依赖仍在整理 | **模块备选**，先验证最小依赖集合，不预设整套接入 |
| [EX-GAS](https://github.com/No78Vino/gameplay-ability-system-for-unity) | MIT；覆盖 Tag、Attribute、Effect、Ability、Cue；依赖付费 Odin Inspector 3.2+；作者说明测试和稳定性仍有限 | **GAS 语义与工具对照**，整体移植改动较大 |
| [sjai013/unity-gameplay-ability-system](https://github.com/sjai013/unity-gameplay-ability-system) | MIT；包含属性、标签与效果；2022-08-13 已归档 | **参考或受控摘取**，不优先用作长期主依赖 |
| [GASify](https://github.com/felipeggrod/gasify) | 有免费版和付费完整版；免费版缺少标签过滤、自定义效果计算等能力 | **暂不优先**；免费仓库未确认明确许可证，公开可读不等于已经取得复用授权 |
| [UGAS / sajad0131](https://github.com/sajad0131/Unity-Gameplay-Ability-System) | MIT；提供属性、技能、叠层效果与 Inspector 配置 | **次级候选**；尚未取得确定性运行、快照与本项目版本的兼容证据 |

### Flexi：最值得先验证制作效率

发布页当前列出的最新版本为 v0.14.1；v0.14.0 说明更新适配 Unity 6000。这是相关兼容线索，不等于已通过本项目 6000.6.2f1 的验证。[发布记录](https://github.com/PhysaliaStudio/Flexi/releases)

其 API 由调用方入队并执行技能；官方自定义节点教程演示把项目对象注入 AbilityContainer，再通过节点调用项目逻辑。这给复用编辑器和流程运行器、接入本项目结算入口提供了具体路径。[API](https://github.com/PhysaliaStudio/Flexi/wiki/API-Summary)、[自定义节点](https://github.com/PhysaliaStudio/Flexi/wiki/2.-Custom-Node)

建议先尝试保留运行器，通过适配节点提交项目认可的命令或效果请求。若必须重写运行器、序列化和绝大多数节点才能接入，应该重新评估收益；不能把“只参考界面后全部重写”算成框架复用成功。

待证事项：运行时程序集的真实 Unity 依赖、节点数据中的对象引用、执行顺序、暂停续作状态、随机源、可规范化的快照、属性计算精度、编辑器资源往返保存。其“核心不依赖 Unity”的说明是项目声明，本次未完成逐文件源码审计。

### AbilityKit：适合考察可独立使用的模块

它并非 UE GAS 的逐项移植，而是更广的战斗工具集。本次仅将触发、标签、属性修改和技能管线列为考察目标。作者明确表示包依赖仍有历史问题，因此“模块化目录存在”不能直接视为“可低成本单独安装”。这些是基于项目文档的候选判断，尚未编译核验。[项目说明](https://github.com/HOBOBO/AbilityKit)

### EX-GAS：概念覆盖较全，接入边界差异明确

读取到的 package.json 标记版本 1.1.8、Unity 2022.3；依赖字段为空，但 README 另行要求 Odin，不能据此认定无外部依赖。[包声明](https://raw.githubusercontent.com/No78Vino/gameplay-ability-system-for-unity/EX-GAS-1.0/Assets/GAS/package.json)

源码中的 AbilitySystemComponent 继承 MonoBehaviour，运行时 asmdef 允许引擎引用。文档还定义了全局 GAS 与 GASTimer。因此，直接把其运行时接进当前纯 C# 内核不符合已有分层；要评估分离组件、替换时钟、效果状态与数值写入边界的成本。[组件源码](https://raw.githubusercontent.com/No78Vino/gameplay-ability-system-for-unity/EX-GAS-1.0/Assets/GAS/Runtime/Component/AbilitySystemComponent.cs)、[程序集](https://raw.githubusercontent.com/No78Vino/gameplay-ability-system-for-unity/EX-GAS-1.0/Assets/GAS/Runtime/com.exhard.exgas.runtime.asmdef)、[核心 API 说明](https://github.com/No78Vino/gameplay-ability-system-for-unity#31-core)

## 建议的职责划分

以下为接入设计建议，不是已经实现的结构。

| 内容 | 建议承担方 |
|---|---|
| 技能资产、节点编辑、模板复用与配置检查 | 尽量复用候选框架及其扩展接口 |
| 标签查询、属性修正与条件触发 | 按模块验证后复用；每类运行状态只有一个权威所有者 |
| 战斗启动前的稳定 ID、数据校验与定义哈希 | 现有 Authoring → BattleDefinition 边界扩展 |
| Tick、ActionPlan、ActorLane、行动窗口权限与肾上腺素 | 现有逻辑系统；普通动作没有时间费用或行动预算 |
| 命中、格挡、闪避、抵抗、冲击和位移结算 | 现有仲裁系统；技能通过明确入口提交请求 |
| 持续效果到期、叠层和移除 | 明确扩展/迁移方案后统一处理，避免两套系统同时推进同一效果 |
| 动画、音效、特效 | 消费逻辑事件的表现层；若复用 Cue，只承担表现职责 |

例如“命中后施加燃烧”：技能资产描述攻击及附加效果；命中是否成立仍由既有仲裁确定；命中事件触发效果申请；燃烧在指定逻辑阶段推进。图节点不能提前绕过格挡直接扣血。

新属性效果还需遵守现有规则：速度变化只影响之后创建的计划，不追溯重算已有计划时序。现有定义中仍含部分 float 输入，不能把项目描述成全面定点数实现；需要复用现有量化与 Q10 边界。[当前玩法](../游戏设计文档.md)

## 最小接入验证

建议先固定 Flexi 的版本/提交，在隔离试验范围验证；若失败，再验证 AbilityKit 的最小模块组合。以下是选型样例，并非本次新增玩法承诺。

1. **现有攻击**：用配置表达一条现有攻击，保持命中 Tick、费用和仲裁结果一致，验证 UI 预览与提交仍同源。
2. **命中附加燃烧**：覆盖周期效果、叠层、刷新、到期、来源追踪与死亡清理。先明确燃烧是否可被抵抗及其结算阶段。
3. **格挡成功触发增益**：覆盖被动触发、条件标签、属性修正和既有计划时序不变。

通过条件：

- Logic 保持无 UnityEngine 引用；权威计时来自 BattleSimulation 的 Tick。
- 同一输入重演得到相同的规范化状态/事件摘要；新增框架状态进入必要的定义哈希与运行时快照。
- 失败或取消不会留下部分扣费、重复效果或未清理的事件订阅。
- 同类技能新增变体可主要通过配置完成，不持续增加核心分支；报告实际复用的编辑器/运行时代码与适配代码。
- 本项目版本下完成导入、资源保存重开、相关 EditMode 验证及目标 Player 编译；性能结论按实际测量记录。

若只节省少量代码、却引入第二套战斗状态和大量维护补丁，应降低该候选优先级。
