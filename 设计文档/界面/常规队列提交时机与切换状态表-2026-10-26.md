# 常规队列：提交、时机与切换状态表（提案）

日期：2026-10-26。状态：提案，对应 2026-10-26 评审的第 1～4 条，属于[分层方案](HUD常规界面与介入界面分层方案-讨论稿-2026-10-17.md) P0a 决策表的一部分；§6 列出需要用户确认的决定。源码事实于同日核对，未运行 Unity。

## 1. 现有实现（作为基线）

| # | 事实 | 依据 |
|---|---|---|
| F1 | 一次普通排程事务内任一项失败即整批拒绝，不存在部分写入 | `ScheduleEditor` 类注释 |
| F2 | 暂停中点“确认”只做预览，草稿进入“待恢复提交”，此时还没有提交 | `BattlePresentationModel.ConfirmDraft` |
| F3 | 恢复时钟后依次执行：① 暂存反应与草稿的合并预览 ② 暂存的并发授权 ③ 普通排程事务 ④ 逐条提交暂存反应。各步是独立命令；某步提交失败即停止并重新暂停（“排程未提交，请调整”），已提交的步骤不撤回 | `BattlePresentationModel.SubmitOnResume`、`BattlePresentationView.ResumePlanning` |
| F4 | 提交成功只代表“待采纳”，下一 Tick 由权威采纳。草稿被拒绝时保留意图，反应显示拒绝原因，两者目前都不自动暂停；授权被接受时会自动暂停，提示可追加普通动作 | 同上，回执处理 |
| F5 | 排程修订号或窗口变化后，草稿在确认时判为过期 | `ConfirmDraft` |
| F6 | 起点为空的新计划请求“权威轨道末尾”，即已有计划的最大末尾，不含本批其他项；同一批多个空起点项按加入顺序依次排开 | `ScheduleEditor.ResolveLaneTailStartTick`、`ScheduleEvaluator` |
| F7 | 给定起点的新计划按请求起点排序放置，与已放置计划重叠时被推到右侧最早可行处，不报错；落入反应硬占用段则整批拒绝；可以从反应的软占用段起手 | `ScheduleEvaluator.EvaluateLane` |
| F8 | 已接受的计划只会被向右推，前项删除后不会左移，只有被直接移动的计划能左移。插入锚点只能指向已注册的计划，不能指向同批候选 | `ScheduleEvaluator`、`ScheduleEditor.ValidateAnchors` |
| F9 | 计划被拼刀等提前终止，排程阶段仍按完整区间占用；终止后不自动前移后续计划 | F6 的轨道末尾口径；游戏设计文档 §4.4 |

F6 与 F7 合在一起有一个陷阱：同一批里混用空起点与给定起点时，空起点项会先占轨道末尾。例如队列为“① 快斩 · 拼刀（给定 6.4 s）、② 重砸 · 尽早（空起点）”，② 请求 6.02 s 并先放下，① 被推到 ② 之后。顺序与时机都被打乱，而且不报错。

## 2. 提交契约

### 2.1 主操作：确认并继续（建议，待确认 D1）

- 常规层与介入层只保留一个主操作按钮。没有暂存内容时显示“▶ 继续”；有暂存内容时显示“确认并继续（行动 N · 反应 M）”，两项分开计数，为 0 的一项省略。
- 只有反应、没有普通动作时也可以确认。
- 点击后依次完成：合并预览 → 恢复时钟 → 按 F3 的顺序提交。合并预览失败时不恢复时钟，就地显示原因。
- 常规层不再显示“待恢复提交”；它只在提交过程中短暂存在。
- 已提交的条目在回执返回前锁定为只读。回执返回后，修改已接受的计划会生成新的编辑草稿，需要再次“确认并继续”。
- 并发授权不经过这个按钮，见 §2.4。

### 2.2 条目状态

| 状态 | 含义 | 可做的操作 | 显示 |
|---|---|---|---|
| 编辑中 | 只在本地，尚未提交 | 加入、移除、修改 | 正常显示，计入按钮计数 |
| 提交中 | 已发出命令，等待下一 Tick 采纳 | 无 | 标“提交中”，锁定 |
| 已接受 | 权威排程中的 Editable 计划 | 移除、改时机（生成新草稿） | 正常显示，不计入计数 |
| 已拒绝 | 权威拒绝，意图保留 | 修改后重新确认、移除 | 红色标记与原因 |
| 已过期 | 排程修订号或窗口变化（F5） | 重新预览后确认、移除 | 标“已过期”与原因 |
| 执行中 / 已结束 | Locked、Running 或终态 | 无 | 移出队列，留在时间轴历史 |

### 2.3 失败与部分提交

F3 的各步彼此独立，Logic 没有跨命令的事务，所以界面不能宣称“要么全部成功，要么全部失败”，而要逐条报告：

| 失败位置 | 已经提交的 | 未提交的 | 界面 |
|---|---|---|---|
| 合并预览 | 无 | 全部 | 不恢复时钟；在出错条目上标原因 |
| 并发授权（仅介入层） | 无 | 普通排程、反应 | 重新暂停；授权区显示原因 |
| 普通排程事务 | 授权（若有） | 普通排程、反应 | 重新暂停；整批标“未提交”，定位到出错条目 |
| 第 k 条反应 | 授权、普通排程、前 k−1 条反应 | 第 k 条及之后 | 重新暂停；已提交的标“提交中”，其余标原因 |
| 下一 Tick 被权威拒绝 | 视具体命令 | — | 建议默认自动暂停并定位（D2），设置中可关闭 |

合并预览已经检查了“普通排程 + 暂存反应”的冲突，所以后几行主要来自预览之后状态又发生变化的情况。若以后需要真正的“一起成功或一起失败”，要在 Logic 增加跨命令的组合事务，属于规则层改动，本提案不做。

### 2.4 并发授权：独立申请

- “申请并发授权”只在他人窗口的介入层出现，显示费用与余额。
- 暂停中申请沿用现有行为：时钟恢复到采纳 Tick，授权被接受后自动暂停，玩家再规划普通动作。申请中、被拒绝、余额不足、窗口过期都有回执。
- 授权申请不与普通排程或反应合并提交。

## 3. 时机与编辑来源

### 3.1 每个条目记录来源

| 来源 | 产生方式 | 起点怎么得出 |
|---|---|---|
| 自动衔接（尽早） | 常规层默认 | 前一项的计划末尾；没有前项时为最早合法起点 |
| 相对时机 | 常规层选择拼刀、抓后摇等 | 由锚点（对方计划 + 命中或末尾等关键点）换算 |
| 精确 | 介入中手动放置 | 玩家给定的 Tick |

- 来源和锚点只保存在界面的草稿条目里，不写进 Logic，AI 与回放都不需要。计划被接受后，界面按计划 ID 继续保留这份记录，直到计划起手。
- 为了避开 F6/F7 的陷阱，界面为每一项都算出起点并显式发送，不再使用空起点。预览后比较“求值起点”与“请求起点”：
  - 自动衔接项：按新结果重排后续项。
  - 相对时机项：标“时机已失效”。
  - 精确项：标“被推后”。

  三种情况都不静默接受。

### 3.2 起点规则

- 自动衔接项与暂存或已接受反应的硬占用段重叠时，起点后移到硬段之后的第一个 Tick（软占用段可用），并标“排在格挡之后”。
- 预计的提前终止（例如拼刀）不改变计划末尾（F9）。下一项仍从计划末尾衔接；位置条同时画出“计划占用到 X”和“预计在 Y 终止”。终止实际发生后能否紧接新计划，取决于终止后轨道占用如何释放，需要在原型中用实际回执确认。
- 从介入返回常规层后新加入的项，接在轨道上所有计划的最大末尾之后。介入中留下的空隙保留、不压紧；需要填空隙时进入介入。

### 3.3 事件 × 来源

| 事件 | 自动衔接 | 相对时机 | 精确 |
|---|---|---|---|
| 前项移除或时长变化（草稿中） | 重新衔接，可前移或后移 | 起点不动；重新检查锚点，以及是否与前项重叠 | 起点不动；重叠时标“被推后” |
| 前项移除（已接受） | 界面在同一笔编辑中显式前移，预览可见（D3） | 不动 | 不动 |
| 锚点计划终止、取消或改变 | — | 标“时机已失效”，保留条目并重新预览；不自动换成别的时机 | — |
| 加入或改动暂存反应 | 按 §3.2 避开硬占用段 | 与硬占用段重叠时标冲突，由玩家选择 | 同左 |
| 打开介入 | 同一计划，动作块上标来源 | 同左，另画锚点连线 | 同左 |
| 在介入中拖动 | 变为精确 | 变为精确，清除锚点记录 | 仍为精确 |
| 返回常规层 | 不变 | 不变 | 不变；新项接在末尾 |
| 排程修订号变化、窗口切换 | 草稿过期，重新预览 | 同左，另检查锚点 | 同左 |

## 4. 切换

| 事件 | 普通草稿 | 暂存反应 | 已接受计划 | 并发授权 | 界面 |
|---|---|---|---|---|---|
| 打开或关闭介入 | 不变 | 不变 | 不变 | 不变 | 只切换呈现方式 |
| 自身窗口结束 | 过期（F5），起点已不在可提交的窗口内 | 保留到截止，过截止作废 | 照常执行 | — | 提示“窗口已结束” |
| 他人窗口结束 | 授权下的普通草稿过期 | 保留到截止 | 照常执行 | 结束 | 授权区显示“已结束” |
| 排程修订号变化 | 过期，需重新预览 | 重新做合并预览 | — | — | 标“已过期” |
| 系统暂停 | 冻结，不提交 | 冻结 | — | — | 恢复后回到原状态 |

## 5. 合法快照约束（示意图与原型）

2026-10-26 评审指出 v4 的情境不可达。按游戏设计文档 §2.1、§3.1、§5，构造快照时必须满足：

1. 普通动作只能由窗口拥有者起手，主角可以另凭并发授权。所以在你的窗口里，敌方不能起手新攻击，只能对你已公开的攻击作出格挡或闪避。
2. 你的窗口里能威胁你的，只有开窗前已起手、命中落在窗口内的攻击。在默认 180 Tick 窗口、前摇不超过一个窗口长度时：
   - 它只可能来自上一个窗口的拥有者；
   - 至多一个，因为轨道串行，第二个动作要等第一个结束才能起手，那时已在窗口之外；
   - 最晚在开窗后一个前摇长度内命中。
3. 可用肾上腺素在该单位自身窗口打开时清零，已接受的反应预留照常履约。因此：
   - 在你的窗口里，开窗时可用值为 0，通常无法再为上述延续威胁新放格挡或闪避。应对手段是拼刀、防守、移动或硬吃。
   - 想格挡它，要在上一个窗口里、威胁刚公开时就放好。那时剩余的可用值反正会在开窗时清零。
4. 反应与自身普通计划冲突，只会出现在他人窗口里、主角凭并发授权排了普通动作的情况。

对“相对时机”三类局面的影响（按 v0.5 候选数值）：

| 局面 | 可达性 |
|---|---|
| 拼刀化解延续威胁 | 自身窗口内可达；开窗时肾上腺素为 0，它是主要应对之一 |
| 抢先打断 | 看到对方起手后再出手做不到：打断要求冲击不低于稳定，候选动作里只有重砸做得到，而重砸前摇 1.5 s，对方的攻击最晚 1.5 s 内命中。只能作为预先承诺：在你的窗口末尾起手，命中落在对方开窗之后，赌对方届时正在前摇 |
| 抓对方后摇 | 对方攻击别人时，你在它前摇或后摇期间命中都一样，它的轨道被占，无法反应。所以“抓后摇”比“尽早”没有额外收益，只在赶不及前摇时才有意义。对正在攻击你的对手，抓后摇意味着先挨这一下；先格挡再抓后摇，快斩会落空 2 Tick |

## 6. 需要用户确认的决定

| # | 建议 | 备选 |
|---|---|---|
| D1 | 常规层与介入层共用一个主操作“确认并继续” | 保留“确认”与“继续”两个按钮 |
| D2 | 任一命令被权威拒绝时默认自动暂停，并定位到出错条目 | 只显示提示，不暂停 |
| D3 | 已接受的自动衔接项，在前项删除后由界面显式前移 | 已接受的计划一律不动 |
| D4 | 常规层与介入层统一使用战斗时钟时间，窗口边界单独标注 | 常规层使用窗口相对时间（分层方案 §3.2 原写法） |
