### 1.2 冻结语义（本轮确立，下游不得改名/复用）

**目的格规则**（`DodgeDestinationRules` + `EvaluateDestination`，顺序固定）：
1. Encounter 边界（`LogicGrid.Boundary.Contains`）⇒ `DODGE_DESTINATION_OUT_OF_BOUNDS`；
2. 位移必须是**单个规范方向的整数步**且 `1 <= 步数 <= MaxDistanceSteps`
   （`0` 步 = 原地 Dodge 合法）⇒ 否则 `DODGE_DESTINATION_TOO_FAR`；
3. 该方向必须被 `DodgePayloadSpec.Pattern` 覆盖（缺席/空集合的方向**不**被覆盖）
   ⇒ 否则 `DODGE_DESTINATION_DIRECTION_NOT_IN_PATTERN`；
4. 完整 footprint（三角 + 格）的边界与**权威占位**（`ValidateDestinationFor`）
   ⇒ `LOGIC_GRID_OCCUPIED_BY_OTHER`；
5. 时间窗冲突：预留窗口固定为 `[ReservedAtTick, TriggerTick]`（**含端点**）；
   与既有移动 Reservation 的 `[StartTick, EndTick)` 相交、或与其他 Dodge 目的格预留相交
   ⇒ `DODGE_DESTINATION_RESERVED_BY_OTHER`。窗口之外（例如 `StartTick >= TriggerTick`
   的纯未来预留）不构成冲突；**权威占位冲突不看时间**（Dodge 无抢占权限）。

**冲突胜者只服从规范命令序**：`ReserveDestinations` 按 `(CommandSequence, ActionPlanId)` 升序处理，
与原始枚举顺序无关；先成功者持有，后到者稳定拒绝、不可抢占。

**原子提交**（`CommitReservation`，阶段 A 零写入预检 → 阶段 B 提交）：
- 阶段 A：`From` 与权威锚点一致（否则 `DODGE_RELOCATION_ORIGIN_MISMATCH`，**零写入**）；
  `ValidateDestinationFor` 与时间窗冲突复检。**防御者自身原因**失败
  （越界/被占/体积非法/预留被抢）⇒ 以 `ActionTerminationReason.TargetInvalid` 终止该反应计划、
  释放目的格预留、**不移动单位**、**不清理任何移动**。
- 阶段 B：`LogicGrid.CommitAnchor`（提交占位变更）+ 释放目的格预留 + 失效依赖移动的
  全部未来段/预留（按 `ActionPlanId` 升序）+ 清空该单位待进入格 + 任务 07 预算释放接缝
  （`BudgetReleaseSink`，**只在真正换位时调用一次**）。阶段 A 已排除全部可失败条件，
  因此阶段 B 在结构上不可能部分提交；若 `CommitAnchor` 仍返回矛盾
  ⇒ `DODGE_RELOCATION_INVARIANT_VIOLATION`（`CommitAnchor` 自身已回滚 ⇒ 零局部写入）。

**未换位不清理移动**：`From == Destination` 时提交成功但 `Moved == false`，
不释放任何段/预留、不调用预算接缝、不改待进入格。

**取消与终态**：来源威胁触发前取消 ⇒ 经统一终态清理槽位
（`SourceThreatCancelled` → 协调器 → `MovementAndReservation` 参与者 →
`DodgeDestinationReservations.ReleaseForPlan`）只释放预留；
`DodgeRelocationAuthority` 同时实现 `IReactionReservationReleaseSink`，可直接接收任务 05 的
释放通知（**装配方当前不接管 `ReservationReleaseSink`**，以免抢走任务 07 的排队语义）。

**任务 08 接口**（不得只给新格）：
- `DodgeSpaceSnapshot CaptureSpaceSnapshot(long tick)`：**任何 Dodge 提交前**的统一只读快照
  （单位锚点/朝向/footprint + 移动 Reservation + Dodge 目的格预留 + 活动段），
  全部为冻结深拷贝 ⇒ 提交之后旧快照仍反映旧位置，旧接触证据不会丢失；
- `DodgeCommitReport BuildReport(tick, before, results)`：提交前快照 + 本阶段全部提交结果
  （`From`/`Destination`/`Committed`/`Code`/`TargetInvalid` 原因）+ 提交后新位置快照；
  `CommittedPositions()` 给出"实际换位的单位 → 新锚点"。
- **不把攻击标为 Dodged**：本任务只做空间提交，接触复核是任务 08 的职责
  （`AreaAttackCanStillHitCommittedDodgeDestination` 证明新格仍可被区域查询命中）。

### 3.4 为什么把比较预算从 64 提到 341 **不是**放宽判据

`ShadowDifferenceDetector.Compare` 在 `legacy.Count > MaxStepsPerComparison` 时**不比较任何字段**，
直接返回 `INVALID:SHADOW_BUDGET_OVERRUN`（`CanClaimEquivalence == false`）。
既有 3 个用例的场景都 ≤ 64 个检查点，因此原值 64 对它们是真实上限；
本用例覆盖**整条移动链**（341 个检查点），沿用 64 只会让报告变成 INVALID——即"比较根本没发生"。

因此 `CompareWithPolicy` 新增**可选**参数 `checkpointBudget = 64`（既有调用点逐字不变），
本用例**从真实检查点数导出预算**并同时断言：

- `shadowSide.Snapshots.Count == budget`（预算不得掩盖一侧缺口）；
- `report.BudgetOverrun == false`（预算必须真的够）；
- `report.ComparedCheckpoints == Task06TerminalTick + 1`（全部检查点都被比较）。

**判据没有变松**：预算只决定"比较是否发生"，不决定"差异是否被报"；下述 **6 个篡改探针**
（其中 4 个属通道 ①②③⑤ 的覆盖证据，另 2 个是**负控制**）全部在放预算之后仍然精确报出各自的字段路径。

### 脚注 C：#56 与 #61 的语义边界（收口轮如实登记）

两项用例**逐名实现并通过**，落地在 `Assets/Tests/EditMode/Authoring/Task06/Task06ScheduleSpaceTests.cs`。
它们守护的**可达**不变量是：

1. 一次排程事务**恰好**推进一个 `ScheduleRevision`（或整批拒绝且零推进）；
2. 段与 Reservation 在**同一批次**里对称替换（数量、归属、StartTick 一致）；
3. Lane 与注册表不留下孤立项；`VerifyInvariants()` 通过；
4. 外部占位（"必须经过的中间格被外部预留占住"）**不会**导致任何部分写入。

**不可达的部分（技术证明）**：`LogicGridMovementAuthority.RebuildMovementSpace` 在写入之前先调用
`ResolveEditableMovementWorkingSet`，后者已经用 `LogicPathfinder.FindPath` 验证过"该计划的候选路径存在"。
因此凡是进入建立阶段的工作集条目，`EstablishMovement` 只可能因三种原因失败：

| 失败码 | 触发条件 | 为何在"经过解析阶段之后"不可达 |
| --- | --- | --- |
| `MOVEMENT_SEGMENT_CHAIN_DISCONTINUOUS` | `path.Count < 2` | 解析阶段已要求 `path.Path.Count >= 2` |
| `MOVEMENT_SEGMENT_INTERVAL_INVALID` | `resolvedBaseStepTicks <= 0` | `TickQuantization.ResolveMoveBaseStepTicks` 对 Move 族保证为正 |
| `LOGIC_GRID_RESERVED_BY_OTHER` / `LOGIC_GRID_RESERVATION_DUPLICATE_KEY` | 目的格同键冲突 | 解析阶段与保留计划使用同一个 `ActionPlanId`，`LogicPathfinder.IsBlocked` 对本计划自己的预留返回未阻塞 |

因此"先建立一个、再中途失败"的**逐项回滚**（`RollbackSpace`）在当前实现下是**防御性代码**，
无法从外部构造出可达失败。两项用例因此**不宣称**覆盖该分支；
若要覆盖，需要给 `IEditableMovementSpacePort` 增加一个测试专用注入口
（会扩大生产可见面），建议由任务 11 决定是否接受。

### 脚注 D：R1 的"同一组请求、不同原始枚举顺序"的比较口径

`ReservationConflictIgnoresRawBatchEnumerationOrder` 比较的是**同一份可观察签名**：
`Envelope` 规范顺序（`seq/prio/ctrl/ord`）+ 已提交计划 + 全部拒绝码 + 段与 Reservation 的完整文本签名。
它**不**比较 `LogicSnapshot` 的十六进制摘要——因为两次运行的事件/快照序号从 1 开始独立分配，

快照摘要的规范序列化另有任务 03 的 `Task03.SnapshotSignature` 覆盖。

### 脚注 A：`PathSearchAllowsExactly4096ExpandedNodes` 的结构证明替代

用例由两部分组成：(a) 用小上限 N 证明**包含式**边界（恰好 3 个展开节点合法、2 个失败）；
(b) 用 `FrozenV1` 证明搜索**真的推进到 4096 个展开节点**（报告值 = 4096，即第 4097 次取出
才触发上限）。**未能构造**"目标恰好是第 4096 个被取出的节点且搜索成功"的场景：
在无障碍一致启发下 `f < C*` 的节点集合为空，展开数只能随目标距离线性增长，
而 192 边 / 256 权重上限把可达距离封在 `x = 448` 以内（见
`PathEdgeLimitReturnsStableFailure` 的走廊分析）；超过该距离的目标一律不可达，
展开数直接跳到 4096 上限。
**结论**：包含式语义已实现并双向验证，但 (a)(b) 是**替代构造**，不是"恰好 4096 成功"的用例。
**可否构造真实用例**：在当前冻结的 `PathSearchRules`（4096 / 256 / 192）下**不可构造**；
除非新增一个"测试专用上限组合"（例如把 `MaxExpandedNodes` 设为一个小值，
再构造一条长度恰好等于该值的走廊）——那需要把 `PathSearchRules` 变成可注入的候选规则，
且会与"上限进入 `BattleDefinitionHash`"的冻结口径冲突。建议归属任务 11 决定是否接受替代构造。

### 脚注 B：`PATH_COST_OVERFLOW` 在 int 坐标下不可达

`PATH_COST_OVERFLOW` 在 **int 坐标 + 4096 节点上限**下**不可达**：
`g/h/f` 的累加不可能逼近 `long` 上限，`HeuristicWeightUnits` 的坐标差也被 int 域封住。
用例改为验证两件可证明的事：(a) 溢出码是冻结稳定码并参与全局优先级；
(b) **真正可达的 checked 溢出**（段时长 `weight × base + startTick`）以
`MOVEMENT_TIMING_OVERFLOW` 整体拒绝且零写入。溢出语义本身已在实现中 checked 化
（`MovementSegment.Create` 的 `checked` 乘法），不是"没写"。
**可否构造真实用例**：需要在 `LogicPathfinder` 之外伪造 `long` 级别的坐标/成本输入，
这在当前的 `GridPoint`（int 坐标）**类型上不可能**；建议保持现状并在任务 11 复核。

### 10.6 冲突回滚：唯一可达失败面的可失败断言 + 不可达分支的技术证明

**可达的失败面（已用可失败断言覆盖）**：真实排程事务在**路径求值阶段**失败时，
必须整批拒绝且**零局部写入**。用例 `AssertTask06FailedBatchLeavesNoPartialWrite` 的构造与断言：

1. 先在一个**全新真实世界**里走同一条脚本化输入，让第一条 Move 计划建立真实段链
   （断言 `SegmentsOfPlan == 9`）；
2. **对照证据**：用真实 `LogicGridPathfinder` 证明"该计划从权威锚点到目的格**确实有路**"
