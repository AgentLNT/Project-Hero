### 3.2 迁移期发现并修正的 8 项自检（避免以"通过"掩盖错误）

本任务在把校验接上真实资产时，先遇到 8 处自身错误，全部**按真实契约修正并留下断言**，未放宽任何规则：

1. MovementPattern identity 表最初用 `(0,0,1)` —— 该点 `X+Y+T = 1` 为奇数，**不是合法三角格点**。修正为 `(1,0,1)`。
2. `GridBoundaryDefinition.ValidPointCount()` 最初用 `(width*height)/2` 向下取整 —— 起点奇偶为偶时会少算 1。修正为解析式 `(total+1)/2` 或 `total/2`（33×33 边界 = **545**）。
3. 动作集合装配函数曾漏加 Guard/Move/Block/Dodge —— 修正后两个集合各 9 个动作。
4. 反应闭合校验曾按"字典键"而非 `spec.ActionSpecId` 查表 —— 修正为按动作自身的稳定 ID 查。
5. `UnitDefinitionValidation` 的字段校验顺序会先于被动抵抗范围报错，破坏任务 02 已冻结的错误优先级 —— 抵抗范围校验提前。
6. `ActionSetId` 为空曾被单定义校验拒绝 —— 该情形属于跨定义引用问题，改由 Builder 的 `DEFINITION_REFERENCE_DANGLING` 负责。
7. `GridBoundary` 曾要求两个端点自身满足顶点奇偶 —— 边界是包围盒，语义由 `Contains` 的奇偶过滤定义，该要求被移除（仅保留"非退化 + 至少含一个合法顶点"）。
8. `PathCostRules` 的偶数方向权重断言曾把 `SouthEast`（索引 10，偶数方向）误写成奇数方向 —— 改为逐向表驱动断言。

> 上述每一项都是"测试先失败、再修正被测契约"的正向过程；没有把测试改成迁就错误实现。

**展开规则（唯一实现：`DirectionalGeometry.ExpandFromBases`）**

- 只使用受检整数 60° 公式：`X' = (X - 3Y - T) / 2`、`Y' = (X + Y + T) / 2`、`T' = -T`。
- 每个基准点连续旋转 0..5 步；偶数方向索引 = East 基准旋 `k` 次、奇数方向索引 = EastNorth 基准旋 `k` 次，交错成严格按 `GridDirection 0 → 11` 排列的 12 向表。
- 每个方向内部按 `(X, Y, T)` 去重 + 升序排序（`DirectionalGeometry.Canonicalize`）。
- **禁止**：回退旧 `GridMath.Rotate`（浮点三角函数）、用偶数基准猜 30° 方向、在 Builder 里用 `Mathf.Sin/Cos`。
- 缺少任一基准 → `DIRECTIONAL_BASE_MISSING`；非法格点 → `TRIANGLE_POINT_INVALID`；受检溢出 → `DIRECTIONAL_EXPANSION_OVERFLOW`；显式序列化方向与展开逐点不符 → `DIRECTIONAL_EXPLICIT_DATA_MISMATCH`（同义码 `DIRECTIONAL_TABLE_MISMATCH`，适配器沿用）。
- 逐向比对证据：`CurrentPatternAndVolumeAssetsMatchLegacyOutputInAllDirections` 覆盖 **13 个资产 × 12 个方向 = 156 个方向**，把每个方向与旧实现的逐向输出逐点比较。
  **旧侧口径（缺陷修复 L2 后）**：不再使用测试内的整数等价物，而是**直接调用旧生产类型** `AttackPattern.GetAffectedTriangles(...)`（`Authoring/Legacy/AttackPattern.cs:18`）与 `UnitVolume.GetVolumeFor(...)`（`Authoring/Legacy/UnitVolume.cs:18`），二者内部调用**真实 `GridMath.Rotate`**（浮点 `Mathf.Cos/Sin` + `RoundToInt`）。因此该比对是"旧浮点旋转路径"与"新受检整数展开路径"两条**独立实现**的交叉验证，而非同公式自证。
  **注意区分**：上条"禁止回退旧 `GridMath.Rotate`"约束的是**生产代码**（Builder 不得用浮点旋转生成定义表）；测试把 `GridMath.Rotate` 作为**旧实现的对照口径**正是其目的，两者不冲突。

## 7. 网格边界与 4096 / 256 / 192 余量

### 7.1 唯一空间边界

| 项 | 值 | 依据 |
|---|---|---|
| Encounter `GridBoundary` | `Min = (-16, -16)`、`Max = (16, 16)` | 场景 `GridVisuals.width = 40`、`height = 20`（世界单位）与相机取景的包围盒；两个初始站位都在其内 |

| 语义 | 顶点包围盒 + `Contains` 的奇偶过滤；`EnumerateValidPoints()` 按 `(X, Y)` 升序稳定枚举 | 三角形级可站立性属任务 06 的 LogicGrid |
| 独立 `MaxSearchDistance` | **不存在** | 任务包明确冻结：Encounter `GridBoundary` 是唯一空间搜索边界 |

### 7.2 冻结搜索上限与余量

| 上限 | 冻结值 | 合法性边界 | 余量（**解析估算**，非任务 01 实测） |
|---|---|---|---|
| `MaxExpandedNodes` | 4096 | `≤ 4096` 合法；`> 4096` 失败 | 合法顶点 545 个 → 整个边界全展开也只有 545 次扩张。**估算余量 ≈ 7.5×**（4096/545 = 7.52），即使搜索退化到遍历全部合法顶点也不会触顶 |
| `MaxPathWeightUnits` | 256 | `≤ 256` 合法 | 两站位 `(-5,-5) → (5,5)`：`dx = dy = 10`，启发 = `10 + max(0, 0/2) = 10` 权重单位；最坏绕行走法约 `2 × 10 = 20` 单位。**估算余量 ≈ 12.8×**（256/20） |
| `MaxPathEdges` | 192 | `≤ 192` 合法 | 同一条路径最坏约 20 条边。**估算余量 ≈ 9.6×**（192/20） |

**这三项余量的性质与来源（必须如实标注）**

- ≈7.5× / ≈12.8× / ≈9.6× 是**由"545 合法顶点"与"`dx = dy = 10`"解析推算**得出的**估算值**，**不是**任务 01 的实测读数。上表"估算余量"一栏的不等式算术可直接复核（4096/545、256/20、192/20）。
- **任务 01 记录中没有这三个量的真实运行期测量条目**（见 `01-基线记录-资产配置与程序集.md`：其内容为资产 GUID/fileID、MonoScript GUID 全表、场景站位等只读基线，不含寻路用量实测）。
- 与任务 01 的关系：任务 01 只提供**只读夹具与签字基线**；本任务据此给出上限与历史余量的**解析估算**。任务 01 的实测值（若有）**未覆盖**任何常量——上限值由任务包冻结，不来自测量。
- **真实运行期测量的归属：任务 06**。届时应实测主场景 `(-5,-5) → (5,5)` 及最坏绕行下的 `ExpandedNodes` / `EdgeCount` / `PathWeightUnits` 峰值，并回来替换本节估算（见 §14 残余项 V2）。

## 8. MovementPattern 的来源（新增内容配置，非从资产推导）

当前项目**没有任何 MovementPattern 资产**：旧系统的 Move 只用逐边时长，没有三角格偏移表，因此不存在"可迁移的旧数据"。

- 最终 ID：`movement.identity`（常量 `MovementPatternIds.Identity`）。
- 内容：12 个方向各自只含**单位自身占据的三角格** `(1, 0, 1)`。
  - 合法性依据：三角格点要求 `T ∈ {-1,1}` 且 `X + Y + T` 为偶数；`1 + 0 + 1 = 2` 为偶数 → 合法。
  - 与方向无关，因此 12 个方向完全一致，可去重、可哈希、可稳定比较。
- 它的唯一作用是让 `MovePayloadSpec` / `DodgePayloadSpec` 有一个闭合、可校验、可哈希的 Pattern 引用；**它不是从资产猜出来的值**，也不是"从旧数据近似得到"的结果。
- 该表**未**参与 `CurrentPatternAndVolumeAssetsMatchLegacyOutputInAllDirections`（那条只比对真实 Pattern/Volume 资产）。

## 10. Faction / Victory / 掩码策略与"旧标志仅作迁移线索"

### 10.1 阵营模型（拍板 A1/A2）

- 阵营清单：`hero`、`monster`（N = 2）。
- 关系矩阵：恰好 `N × (N-1) / 2 = 1` 条规范无序对 → `hero ↔ monster = Hostile`（`FactionAId = hero` 按 Ordinal 严格小于 `FactionBId = monster`）。
- 自动成立、不占矩阵条目：同 `FactionId` 的不同单位 = `Allied`；同一 `UnitId` = `Self`。
- 缺失/重复/反向重复/自关系/悬空分别以 `FACTION_RELATION_MISSING` / `_DUPLICATE` / `_NOT_CANONICAL` / `_UNKNOWN_ID` 拒绝；**不得**用 Hostile 或 Neutral 补洞。
- 解析器语义（`FactionRelationResolver`，Logic 内唯一关系查询入口）：Self → 同 faction → 跨阵营矩阵；跨阵营关系缺失是运行时不变量错误（`FACTION_RELATION_INVARIANT_VIOLATION`），**不退回 Neutral/Hostile 后继续**。

### 10.2 逐攻击目标掩码（拍板 A3）

- 10 条攻击全部 `AllowedTargetRelations = { Hostile }`。
- **掩码由迁移清单逐条人工确认后传入 Builder**；Logic 侧没有"默认只打敌人"的兜底。掩码为空 → `ATTACK_TARGET_RELATION_MASK_EMPTY`；含未定义位 → `ATTACK_TARGET_RELATION_MASK_INVALID`。
- 结构保留 `TargetRelationMask.Self | Allied | Neutral | Hostile` 全位扩展能力；本期不配置友伤。改掩码 = 改配置（哈希随之变化），不改引擎。

### 10.3 胜负（拍板 A4）

| 项 | 值 |
|---|---|
| Allied 目标组 | `{ hero }` |
| Hostile 目标组 | `{ monster }` |
| 结果码 | Victory = `victory`、Defeat = `defeat`、Draw = `draw`（三者都显式写入定义并进哈希） |
| 校验 | 两组非空、互不相交、只引用已定义阵营；Allied 组内部互为 Allied、每个 Allied—Hostile 跨组对互为 Hostile；缺失结果码 → `VICTORY_RESULT_CODE_MISSING` |
| Hostile 组内部 | **不附加关系约束**（保留矩阵原值） |
| 目标外阵营 | 不参与消灭条件，但仍保留矩阵中的真实关系；**不得**被一概改写为 Neutral |

### 10.4 旧标志的处置：只作迁移线索

| 旧事实 | 在新模型中的位置 | 是否影响敌我/胜负 |
|---|---|---|
| `CombatUnit.IsPlayerControlled` | **仅**在 `LegacyCombatUnitStatsReader.ReadFromActiveScene` 中作为"定位旧场景对象"的线索（调用方也可显式指定哪个是 hero 槽位） | **否**。它不进入 `BattleDefinition`、不进入 `BattleRuntimeInputs`、不进入哈希、不被 Logic 读取 |
| 旧 Controller / GameObject 名 / 场景注册顺序 / `GetInstanceID()` / 随机 GUID | 全部不得作为逻辑 ID | **否**。初始化器与 Builder 的公开 API 都不接受它们 |
| 旧 `GetUnitsInArea` 的"命中任意非自身单位" | 迁移为 `TargetPolicy.AllTargetsInArea` + 显式掩码 | 掩码是唯一的目标资格来源 |

### 10.5 动态生成阵营策略

- `DynamicSpawnFactionPolicy` 只允许两种可解析形态：`InheritSourceFaction = true`（显式继承召唤者阵营）或 `FixedFactionId` 非空。
- 首版默认 = `InheritSource()`。
- 固定策略但 `FactionId` 为空 → `DYNAMIC_SPAWN_POLICY_INVALID`；**没有**"缺省 = Hostile/Neutral"的兜底。
- 命令、Controller、View、`IsPlayerControlled` 都不得提供或改写动态生成单位的阵营。
