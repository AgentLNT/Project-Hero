## 1. 冻结契约 1：`UnitState` 与状态机转换矩阵

### 1.1 状态集合（`enum UnitState`，值即快照编码）

| 值 | 状态 | 语义 |
|---|---|---|
| 0 | `Idle` | 空闲（唯一无限持续的中性状态） |
| 1 | `Windup` | 前摇 |
| 2 | `Recovery` | 后摇 |
| 3 | `Moving` | 移动中 |
| 4 | `Guarding` | 计划格挡（**不自带免伤**） |
| 5 | `Blocking` | 反应格挡（**不自带免伤**） |
| 6 | `Dodging` | 闪避（**不自带免伤**） |
| 7 | `Staggered` | 硬直（有限控制状态） |
| 8 | `KnockedDown` | 击倒（有限控制状态） |
| 9 | `Recovering` | 恢复槽位（**已声明但首版不作为默认到期目标**） |
| 10 | `Dead` | 终态 |

### 1.2 转换矩阵（`UnitStateMachine.DeclaredTransitions`，**32 条**，逐条如下）

| 来源 | 允许目标 |
|---|---|
| `Idle` | `Windup`、`Moving`、`Guarding`、`Blocking`、`Dodging`、`Staggered`、`KnockedDown` |
| `Windup` | `Recovery`、`Staggered`、`KnockedDown` |
| `Recovery` | `Idle`、`Staggered`、`KnockedDown` |
| `Moving` | `Idle`、`Staggered`、`KnockedDown` |
| `Guarding` | `Idle`、`Staggered`、`KnockedDown` |
| `Blocking` | `Idle`、`Staggered`、`KnockedDown` |
| `Dodging` | `Idle`、`Staggered`、`KnockedDown` |
| `Staggered` | `Idle`、`Recovering` |
| `KnockedDown` | `Idle`、`Recovering` |
| `Recovering` | `Idle`、`Staggered`、`KnockedDown` |
| `Dead` | **（无出边：终态）** |

**接受集合的封闭定义**（`UnitStateMachine.IsValidTransition` 的枚举真值）：
`接受 = DeclaredTransitions ∪ {任意非 Dead → Dead}` ⇒ 32 + 10 = **42 / 121 组合**，其余一律以稳定码拒绝。

**两条重要推论（后续任务必须遵守）**：

- `Recovery` **只能**由 `Windup` 进入；`Recovering` **只能**由 `Staggered`/`KnockedDown` 进入。任何"从 Idle 一步进任意状态"的假设都是错的（本任务的测试夹具曾因此失败，见 §6 D3）。
- `Dead` 是终态：不接受任何出边（含"到期回 Idle"），`Advance` 对其永不生效。

**拒绝原因码（稳定）**：`STATE_TRANSITION_SAME_STATE`、`STATE_TRANSITION_FROM_TERMINAL`、`STATE_TRANSITION_NOT_DECLARED` 等，全部由 `UnitStateCodes` 常量提供；被拒绝的转换**不修改状态、不发事件**，只递增 `RejectedTransitionCount` 诊断计数。

### 1.3 显式与自动到期走同一入口

- 唯一写入入口是 `TryTransition(spec, tick, reasonCode)` → `TransitionOutcome(applied, rejectionCode, from, to)`。
- 自动到期由 `Advance(tick)` 触发，内部调用**同一**入口，只是原因码为 `UnitStateTransitionReasons.AutomaticExpiry`；发射的事件类型相同（`UnitStateChangedEvent`），形状相同（唯一的差别是 ReasonCode 与目标状态）。
- 原因码全集：`UnitStateTransitionReasons.Explicit` = `STATE_TRANSITION_EXPLICIT`、`AutomaticExpiry` = `STATE_TRANSITION_AUTOMATIC_EXPIRY`、`Death` = `STATE_TRANSITION_DEATH`。

## 2. 冻结契约 2：半开区间、到期与只读阻塞事实

### 2.1 半开区间

- 状态区间：`[StateStartTick, StateEndTick)`，`StateEndTick = StateStartTick + DurationTicks`。
- `DurationTicks == 0` ⇒ **无限持续**，`StateEndTick = long.MaxValue`、`NextOnExpire == null`、`HasFiniteEndTick == false`；`DurationTicks > 0` **必须**显式给出 `NextOnExpire`，否则 `Validate()` 返回 `STATE_TIMED_TRANSITION_MISSING_NEXT_ON_EXPIRE`（**不允许隐式默认回 Idle**）。
- `DurationTicks == 0` 同时给出 `NextOnExpire` 也被拒（`STATE_DURATION_MUST_BE_ZERO_WITHOUT_NEXT_ON_EXPIRE`）。
- 到期语义：`Advance(T)` 在 `T == StateEndTick` 即转换（**先转换、不多停留一 Tick**），新状态从 `T` 开始，原因码自动到期。

**01B 决策 B2 冻结值**：`UnitStateMachine.StaggerFor(30)` → `Staggered` 持续 30 Tick、到期回 `Idle`；`KnockDownFor(60)` → `KnockedDown` 持续 60 Tick、到期回 `Idle`。

### 2.2 只读有限启动阻塞查询（任务 05 的唯一接口面）

任务 04 为任务 05 提供**只读事实**，不给任何写入/延期权威：

| 成员 | 类型 | 语义 |
|---|---|---|
| `CurrentState` | `UnitState` | 当前控制状态 |
| `HasFiniteEndTick` | `bool` | 是否存在有限结束 Tick |
| `BlockingUntilTick` | `long?` | **权威阻塞边界**：有限状态时为 `StateEndTick`；无限持续或 `Dead` 时为 `null` |
| `NextOnExpire` | `StateTransitionSpec` | 到期目标（`null` = 无限） |
| `CanReceiveDirectHit` | `bool` | 见 §2.3（**不是**通用交互资格） |
| `PreviousState` / `StateStartTick` / `StateEndTick` | — | 只读区间端点 |
| `RejectedTransitionCount` / `AutomaticExpiryCount` | `int` | 只读诊断 |

**`BlockingUntilTick` 必须直接来自状态实例的权威结束边界**，不是 `StateStartTick + 1` 之类的近似（测试 `StateMachineDoesNotExposeSubmissionAuthority` 用 `Not.EqualTo(StateStartTick + 1)` 钉死），门禁因此可以立刻放行而不必"下一 Tick 再试"。

**结构性禁止**（测试 `StateMachineDoesNotExposeSubmissionAuthority` + `StateMachineExposesDirectHitEligibilityNotInteractionParticipation` 用反射穷举）：

- 禁止出现 `CanExecuteImmediately`、`CanSubmit`、`CanAcceptPlan`、`CanStartPlan`、`CanDefer`、`ShouldDefer`、`RetryAtTick`、`CanSubmitNewAction`、`AllowsNewPlan` 等提交/延期权威成员；
- 禁止出现 `IsTargetableByInteraction`、`CanBeInteractedWith`、`CanBeTargeted`、`IsValidTarget`、`IsInteractive` 等**通用交互资格**成员；
- 全部公开成员不得以 `Set` 开头（状态机没有任何写入面）。

### 2.3 `CanReceiveDirectHit`：只回答直接命中，不回答特殊交互

冻结真值表（`UnitStateMachine.CanReceiveDirectHitIn`）：

| 状态 | `CanReceiveDirectHit` |
|---|---|
| `Idle` / `Windup` / `Recovery` / `Moving` | **true** |
| `Guarding` / `Blocking` / `Dodging` | **true**（防御状态**不自带免伤**） |
| `Staggered` / `KnockedDown` / `Recovering` | **false**（首版规则） |
| `Dead` | **false** |

**防御状态不自带免伤的契约**（测试 `DefenseStateAloneDoesNotMitigateOrInvalidateContact`，任务包必需测试）：

- 三个防御状态的 `CanReceiveDirectHit` 均为 **true**：Guard 的部分抵抗来自**计划 Active 区间**；Block 的完全抵抗来自**匹配 TriggerTick 的反应 Intent**；Dodge 的避伤来自 **TriggerTick 原子换格后的空间复核**。状态本身**不提供**任何免伤面。
- 状态机**不含**任何减伤/免伤/接触失效成员（反射穷举拒绝 `DamageMultiplier`、`Mitigation*`、`Resistance`、`NegatesDamage`、`InvalidatesContact`、`Immune`、`AvoidsHit`、`BlocksContact`、`DodgesContact` …），也没有任何接收伤害的输入面（无 `ApplyDamage(Q10)`、无 `SetHealth`）。
- 行为对照：处于 `Guarding` 的单位**仍可被接触结果改写状态**（`Guarding → Staggered` 被接受），而 `Staggered` 自身转为拒绝直接命中——两条事实构成对照，证明"免伤来自区间/Intent/空间复核"而不是来自状态。

⚠️ **任务 08 的硬约束**：`CanReceiveDirectHit` **只**在 Remaining Hit 阶段被查询；不得用它实现或提前过滤 Guard/Block/Dodge 的效果，也不得把它当作计划提交资格。

## 3. 冻结契约 3：持续效果内核、死亡与胜负

### 3.1 效果内核（`BuffSystem`，任务 04 后**唯一**的效果推进器）

| 契约 | 内容 |
|---|---|
| 实例身份 | 每个可独立移除/到期的实例有唯一 `EffectId`（由 `LogicIdGenerator.NextEffectId` 分配、单调递增、**不回卷不复用**）；`NextEffectId` 进入规范化快照 |
| 配置身份 | `StatusEffectSpecId`；同一配置可被多次施加，实例之间互不影响 |
| 稳定排序键 | **`AppliedAtTick → EffectSequence → EffectId`**（`EffectId` 仅作同键兜底；实际不可能相等） |
| 半开区间 | `[AppliedAtTick, AppliedAtTick + DurationTicks)`；**到期 Tick 先移除、不额外触发一次效果** |
| 跨单位顺序 | 按 **`UnitId` 升序**遍历与报告（传入的宿主数组顺序无关；`EffectAdvanceReport.ExpiredEffectIds` 同序） |
| 延迟队列 | 遍历中的增删一律进延迟队列，遍历结束后**原子**提交；提交顺序 = `(UnitId, Kind: Apply 先于 Remove, 稳定键)` |
| 回调约束 | 载荷回调**从不**直接修改活动集合（结构上不可能：所有写入只发生在 `DrainPending`） |
| 事件 | `StatusEffectAppliedEvent` / `StatusEffectRemovedEvent`（后者带 `Expired` 标志，显式移除与到期可区分） |
| 载荷分派 | 唯一分派点 `ApplyPayloadOnTick`；未知载荷类型**抛** `EFFECT_DEFERRED_OPERATION_UNKNOWN`（fail-closed，扩展必须显式加入） |
| 首版载荷 | `NoOpEffectPayload`、`DamageOverTimeEffectPayload(DamagePerTickQ10)` |

**非遍历期语义**（本任务修复的缺陷 D1，见 §6）：`Apply()` 在非遍历期**立即提交**，并以**本方法收到的 `currentTick`** 发事件——首次推进之前施加的效果同样必须留下"施加"事件，不能静默丢失。

**重复移除语义**：延迟期间对同一实例重复请求移除**仍被接受**（返回 `true`，后置条件"该实例将被移除"成立），但提交时**只生效一次**——只发一条移除事件、活动集合只被改动一次。

### 3.3 阶段边界（任务包「必须产出」6 的两段死亡判定）

**`[04-FROZEN-STAGE2-COMMIT]`（修订轮 R1 冻结结论：以代码真实行为为唯一权威；任务 05 的阶段 2 完成语义必须依赖这四条；此块与 `BattleSimulation` 类文档注释、`Task04Fixture` 顶部笔记逐字一致）**

> **修订说明（R1）**：本节旧版曾写作"阶段 2 生命 ≤ 0 ⇒ 进入终态 `Dead`、发死亡事件、置 `DeathProcessed`，**但 `IsAlive` 仍为 `true`**"，与代码真实行为不符（`IsAlive` 的唯一写点是 `BattleSimulation.cs` 的 `ProcessDeaths`，与 `DeathProcessed` 成对写入），也与 `Task04Fixture` 已有的正确描述自相矛盾。现以代码为唯一权威统一表述；**实现未改动**（判断依据：文档描述的那个中间状态既无人消费也无测试依赖，改成文档描述反而会引入"死亡已提交却仍在场"的第二个写点，并使"每单位恰好一条通知"失去原子性）。逐条证据见 §13。

| 判定点 | 阶段 | 语义 |
|---|---|---|
| 命令前判定 | **2** `DeathAndVictory` | 只回答"本 Tick 打开窗口之前战斗是否已结束"。判定为真 ⇒ **先把本 Tick 致死单位按阶段 15 的完整语义提交**（终态、事件、一次性通知、占位移除），再设 `_resolvedResultCode = 配置结果码`，对已冻结批次发稳定拒绝码 `COMMAND_BATTLE_ENDED_BEFORE_COMMAND_PHASE`，然后进入唯一 Finalizer。**阶段 3–17 全部不执行**（含阶段 11–13 位移与阶段 15）。 |

**同 Tick 致死单位的规则（冻结）**：

- 致死单位在阶段 11–13 **仍以"在场"身份参与同时强制位移求解**（死亡提交前 `IsAlive` 保持 true，`UnitSnapshot.IsAlive` 亦然）；它作为障碍物阻挡同 Tick 的其他单位，且该阻挡**不因它本 Tick 会死而改变**。**注意这是条件性事实而非结构性保证**：仅当阶段 2 命令前判定为假（战斗继续）时阶段 11–13 才会执行；判定为真时阶段 2 已完整提交死亡并直接进入 Finalizer（冻结结论 ③）。
- 死亡系统只读取**换位后**的最终位置：`UnitLifecycleCleanupNotice.FinalPosition` 是 `ApplyBatchRelocation` 已提交的**换位后**位置；`LastDeathFootprintRemovals` 移除的是最终 footprint。
- **位移事件严格先于死亡事件**（测试 `LethalForcedDisplacementCommitsBeforeDeathRemovesFinalOccupancy` 用事件序号比较钉死）。
- 致死单位的"战斗效力"由 `IsCombatEffective`（`IsAlive && !DeathProcessed && HealthQ10 > 0`）表达，胜负判定只用它，不用 `IsAlive`。`DeathProcessed` 对存活单位是**冗余防御位**（恒有 `DeathProcessed == !IsAlive`），不是独立的阶段产物。

### 3.5 胜负：职责边界、矩阵与结果路由
