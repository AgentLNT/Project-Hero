## 决策一：阵营模型与逐攻击 AllowedTargetRelations

### 1.1 证据（为什么必须决策）

| 证据 | 位置 | 结论 |
|---|---|---|
| 旧唯一"阵营"事实 = `IsPlayerControlled` 布尔 | CombatDemo.cs:52 | 单布尔承担阵营/胜负/AI 目标/命令权限/反应特权五重职责（运行时记录 §15） |
| 旧命中候选 = `GetUnitsInArea` 任意非自身单位 | AttackIntent.cs:51-52 | 代码层面"能打友军"，但 1v1 demo 无法证明设计意图 |
| 设计文档：队友系统（指挥队友、时间轴对齐队友伤害帧） | Game_Design_Final.md:225-249 | **多友军单位是核心设计**，Allied 关系必须现在建模 |
| 设计文档：队友 AI 自动规避 AoE | Game_Design_Final.md:247 | 敌方 AoE 对队友是真实威胁 → AoE 伤害友方目标的语义在设计中存在 |
| 主方案冻结：FactionModelDefinition 显式静态对称关系，同阵营=Allied、同单位=Self | 主方案落地修订 25、00-规则 30 | 机制已定，缺的是**具体阵营清单与每个攻击的掩码值** |
| 主方案冻结：Attack 用非空 TargetRelationMask 声明可影响关系；EncounterUnitSlot 携带稳定 FactionId；胜负只看 VictoryDefinition + 显式 Draw | 落地修订 25/26、00-规则 30/31 | 同上 |
| 无任何中立阵营/中立单位的设定证据 | 设计文档全库 grep | Neutral 是模型预留，本期无内容 |

### 1.2 需拍板的子决策

**A1. 阵营清单（FactionId 取值）**
- 选项 a（推荐）：`hero`（主角+队友）、`monster`（敌方）。与设计文档多队友结构一致；demo 只有 2 单位，各自 1 个阵营。
- 选项 b：额外现在建 `neutral` 占位阵营。不推荐——00-规则 30 要求矩阵声明**每对不同阵营**，占位会强制声明两对无内容的 Neutral 关系，徒增配置与测试面。
- 影响：02B `BattleDefinitionBuilder` 的 FactionModelDefinition 内容与完备性校验。

**A2. 关系矩阵**
- hero↔monster = Hostile（唯一无序对）。同阵营 Allied、同单位 Self 由规则自动成立，无需配置。
- 无实质分歧，仅确认命名。

**A3. 逐攻击 AllowedTargetRelations（核心决策）**
| 攻击 | 旧行为 | 选项 a：全 Hostile-only（推荐） | 选项 b：Whirlwind 开友伤 |
|---|---|---|---|
| QuickSlash / HeavySmash / WideCleave / SpearThrust | 命中任意非自身单位 | Hostile（无友伤） | 同左（这四个无争议） |
| Whirlwind（360° 环形 Pattern） | 同上 | Hostile（无友伤） | Hostile \| Allied（可误伤队友） |
- 依据：设计文档"队友规避 AoE"说明 AoE 威胁真实，但那是**敌方攻击打队友**（敌→hero 方向本来就是 Hostile），不直接证明**玩家的 Whirlwind 应该误伤队友**。
- 推荐选项 a：本期全部 Hostile-only，1v1 demo 零风险；`TargetRelationMask` 结构天然支持未来改成 Hostile|Allied，**改配置不改引擎**。等队友内容上线时再按玩法需要开放 Whirlwind 友伤。
- 若选 b：02B 需要为 Whirlwind 的掩码单独配置，并在 08 的 AOE 候选测试中增加友伤用例。
- 影响：02B 迁移表、08 候选构建与测试矩阵、09 AI 选目标（AI 需评估友伤代价）。

**A4. VictoryDefinition（demo 胜负）**
- 选项（推荐）：Allied 目标组={hero}、Hostile 目标组={monster}；双方同 Tick 全灭走主方案 DrawResultCode。
- 影响：04 胜负测试（含 Draw 用例）。

## 决策二：伤害/动量迁移的 5 项歧义

### 2.1 已由主方案冻结、无需决策的部分（对照结论）

| 项 | 冻结内容 | 与旧行为的关系 |
|---|---|---|
| 伤害通道清单 | 首版内置 `physical.blunt/slash/pierce`、`elemental.fire/frost/lightning`、`arcane`、`true`（0.4.2.1） | 旧 ImpactType 拆为 Channel+Profile；通道清单本身无争议 |
| 动量量化公式 | `Mass×MomentumSpeed×ForceMultiplier×ImpactTransferPercent`，一次量化，`MomentumUnitsPerLegacyMomentum=100` | 与旧公式等价（F1 已验证） |
| ArmorDefense 换算 | `BaseDamageResistanceQ10[物理通道]=1024×armor/(armor+100)`（0.4.2.1：只转对应物理通道基础抵抗） | 旧非线性公式在 Authoring 边界一次性折算；demo armor=0 → R=0，无实际数值变化 |
| 冲击伤害系数 | Normal=动量/5000、Clash 剩余=/1000 | 与旧 ×0.02/×0.1 逐位等价（F1/F3 已验证） |
| 硬直/击倒/击退阈值 | `CRU=max(1,RoundHalfUp(M×S×100))`；Stagger=CRU、Knockdown=ceil(1.5×CRU)；Steps=floor(Resultant/CRU) | **数学等价证明**：p'=100p ⟹ 旧三档（≥1.5×/≥1.0×/>0.5×v_t）与新三档逐位一致；旧第三分支位移 floor∈[0.5,1.0)=0，与新 Steps=0 完全一致，无需保留特殊分支（F1 已验证 144000≥135000→击倒、1 格） |
| 表现副作用（伤害数字/震屏/顿帧/弹跳/状态图标） | 逻辑事件只描述事实，表现归 UnityView 适配器（落地修订 9、00-规则 10） | 不进入 Channel/Profile 映射——**无需决策**（原歧义 4 消解） |
| 无事件总线 | 任务 03 建 LogicEventOutbox | 基础设施缺口，**无需设计决策**（原歧义 5 消解） |

### 2.2 仍需拍板的子决策

**B1. MagicResistance 处置（原歧义 1，证据已更新）**
- 代码事实：全项目唯一出现点即声明处（CombatUnit.cs:78），零读取，场景值=0——任务 01 因此标"死字段"。
- **新证据**：Game_Design_Final.md 明确规划魔法系统——§V:106"魔法抗性 INT/WIS 抵御元素和法术锐度伤害"、§V:166 $D_{magic}=D_{spell}×(1−MR/(MR+100))$、§V:186 弹性吟唱、§V:371 魔法动量。→ MagicResistance 是**规划内未实现**字段，不是死字段。
- 选项 a（推荐）：迁移为 `BaseDamageResistanceQ10[elemental.fire/frost/lightning]`（如未来有 magic 通道再分）的候选来源，沿用 armor 同款换算 R=1024×MR/(MR+100)。当前值 0 → R=0，本期无实际数值影响，但保留了设计意图与换算约定。
- 选项 b：本期删除，等魔法系统落地时重新设计。代价：设计文档中的 MR 语义在迁移链中留白。
- 衍生说明：设计文档写 MR 由 INT/WIS 派生，旧字段是独立序列化值；"属性→抗性"派生规则属于未来单位定义设计，本期不处理（demo 值=0 无影响）。
- 影响：02B 迁移表与定义哈希（选 a 则 elemental 通道各多一个 0 值配置项）。

**B2. 受控状态恢复语义（原歧义 2 的剩余部分）**
- 阈值本身已消解（见 2.1 表）。
- 真正的分歧：**恢复如何发生**。
  - 旧：Stagger/Knockdown 无时长，玩家点 Recover / AI ScheduleRecover → `RecoverIntent` **瞬间清零三标志**（RecoverIntent.cs:17-26）。
  - 新（主方案 rule 24）：`Staggered` / `KnockedDown` / `Recovering` 是**有明确结束 Tick** 的定时状态，到期自动恢复。
- 选项 a（推荐，与主方案一致）：自动定时恢复。需给出时长，提案默认值（旧系统无任何时长数据，纯提案）：Stagger=30 Tick（0.5s）、Knockdown=60 Tick（1.0s）。
- 选项 b：保留"手动 Recover 动作"——与主方案统一动作族（Guard/Block/Move/Dodge+攻击）冲突，需修订主方案，不推荐。
- 影响：任务 04 状态机终态与 EndTick、07 启动门禁阻塞期、09 AI 决策（旧 AI 的 ScheduleRecover 分支整体移除）。

**B3. 肾上腺素规则数值（原歧义 3）**
- 旧行为（characterization）：攻击者 +0.1×totalDamage、受击者 +0.2×totalDamage、Clash 承伤者 +0.5×impactDamage、上限 100、**每帧衰减 5/s**。
- 新规则（主方案 0.1 已冻结公式与约束）：DealtGain/ReceivedGain 用 Q10 比率，Clash/Block/Dodge 成功给**固定奖励**；受 MaxAvailablePerCycle 约束；Block/Dodge 奖励必须 < 对应费用；Available 不衰减、自身窗口打开时清零（**旧衰减行为确认移除**）。
- 需拍板的数值（全部进 BattleDefinitionHash）：
  1. `DamageDealtGainQ10` / `DamageReceivedGainQ10`：候选 **102 / 205**（≈旧 0.1/0.2）。
  2. `ClashReward`：旧是**比例**（0.5×impactDamage），新是**固定值**——需选代表值。参考：典型 Clash 夹具 F3 旧给 +50.4；候选区间 20~50（取 50 则与 F3 量级一致）。
  3. `MaxAvailablePerCycle`：候选 **100**（=旧上限）。
  4. Block 费用 / Dodge 费用（肾上腺素）：旧用 Focus（Block 2 / Dodge 1），货币不同仅作比例参考；候选沿用 **2 / 1**。
  5. `SuccessfulBlockReward` / `SuccessfulDodgeReward`：须分别低于对应费用，候选 **1 / 0** 或 **1 / 1**（Dodge 费用 1 时必须 0，或同时上调 Dodge 费用）。
  6. Block/Dodge `ReactionWindupTicks`：候选 **60 / 30**（源自场景值 BlockDuration=1.0s、DodgeDuration=0.5s）。
- 影响：07 肾上腺素账本测试（Cycle/预留/上限）、08 反应奖励结算、09 AI 反应评分。
