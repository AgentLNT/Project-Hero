# 偏好互打、长局与距离扩围方法

本轮是用户授权的第三项，接续任务 19 防御评价及任务 20 主动接近目标。目标是用实际战斗结果判断策略、权重和战斗数值的问题来源；正确性测试通过不代表参数校准完成。

## 固定起点与矩阵

`NewBattleSimulationSource.BuildSeed()` 从真实 `CombatSampleScene` 构建正式定义。`FormalAiMatchup` 只改变本轮对照的控制者偏好和出生几何，所有正式动作、单位属性、动作集、伤害规则和资源规则复用原定义对象；双方都通过注册 AI 入口自主决策。首次对照使用 `AiForecastSettings(360, true, true)`，同时启用前两项改进。

三种偏好分别分配给英雄与怪物，共 9 个有序组合，每组有以下三种布局和两种 180° 镜像，共 54 场。先完成 1800 Tick 探索矩阵（97,200 Tick，全部尚未结束），再把最终上限延长为 3600 Tick，即 60 秒逻辑时间；不是把截断当作平局：

| 布局 | 未镜像出生中心 | 初始曼哈顿距离 |
| --- | --- | ---: |
| Near | 英雄 (-4, 0)，怪物 (4, 0) | 8 |
| Main | 原正式场景：英雄 (-5, -5)，怪物 (5, 5) | 20 |
| Far | 英雄 (-12, -8)，怪物 (12, 8) | 40 |

Main 原始朝向保留；Far 英雄朝东、怪物朝西。镜像同时反转出生坐标并旋转朝向，不改变攻击资产。不同距离也带有几何/朝向差异，不能据此单独估算纯距离的因果效应。

正式英雄与怪物的体积和招式集有差异。偏好交换分配后分别处于两种角色及其生产先手顺序；`owners.csv` 记录真实首个窗口所有者。镜像只是几何对照，不冒充先手交换，也不把两种角色的结果混为对称策略胜率。

使用场景原种子及初始元资源。当前效用选择使用稳定排序；本轮单一种子不构成随机种子扩围。时间截断与自然胜负严格分开，不把未结束算成平局。

## 指标口径

`summary.csv` 汇总每场原始指标；逐场保留 `input.json`、权威回放、候选/决策/事件压缩日志以及以下明细：

- `checkpoints.csv`：240、900、1800、3600 Tick 或自然结束时的生命、真实累计生命损失、攻击启动和正伤害接触等；用于观察早期表现是否延续。
- `actions.csv`：动作实际锁定启动次数、结算后正伤害接触次数与解析伤害。攻击提交、攻击启动、命中分别统计；解析伤害与原始快照降幅均可能含过量伤害，不能当作按生命零点截断的有效损失。
- `resources.csv`：实际入账、消费、自己窗口周期清零损失、周期数及退款。不能用最终余额代替资源收入速度。
- `waits.csv`：实际没有选中命令的决策 Tick，按控制者和原因计数，包含窗口、节奏及任务等待；不能把全部等待合称消极策略。
- `owners.csv`：英雄/怪物单位 ID 及真实第一个窗口所有者。
- `timing.txt`：工具运行的诊断墙钟耗时，受并行和机器状态影响，不用于正式性能验收。

原始 `healthLossQ10` 按前后权威快照差额累计；内核生命可以为负，故它包含过量伤害。派生 `effectiveHealthLossQ10` 对生命零点截断，`overkillQ10` 单列两者差额。本矩阵每单位初始 200 生命，没有治疗/动态增援，可由起终生命独立核对。首次/末次伤害 Tick 只读取生命下降；末次进展指生命变化或位置变化，不把攻击命令本身当作战斗进展。候选日志保留原效用、无应对效用/伤害、最差防御及覆盖状态，以便区分无候选、评分问题和应对模型问题。

## 独立审计

原生 Unity Pilot 在完成 4 场近距 1800 Tick 样本后停止，完整样本与当时源码保存在 `unity-reference/`；未完成文件不作证据。Mono 执行耗时较长，完整矩阵改用 .NET 10.0.11 执行相同 Logic 源码，Unity CLI 仍用于正式定义导出与原生测试。`harness/FormalAiSourceExport.cs` 由 Unity 对真实定义逐字段机械导出，启动时重算原定义哈希，必须为 `84116d595d222a72`。没有手写另一套战斗规则。

`harness/build.ps1` 使用 PowerShell 7.6.5 自带 Roslyn，编译原 `Assets/Scripts/Logic/**/*.cs`（仅排除现代 .NET 不需要的 `IsExternalInit` 兼容声明）、原纯数据校验器、正式互打输入构建器和本轮工具。`Shims.cs` 只适配 Unity 日志/JSON 与宿主类型，不替换战斗实现；`build-manifest.json` 保存参与编译的源码哈希及程序集哈希。工具不进入正式 Runtime 配置。

先由 .NET 对上述 4 场 Unity 样本作跨运行时核对，共 7200 Tick：逐 Tick 事件规范编码和完整快照哈希、候选/决策日志、全部逐场指标必须一致。不能把这项交叉验证表述为 54 场都在 Unity 内执行过。

完整生成之后，`FormalAiMatchupTools.Audit` 在另一个 .NET 进程重建全部输入，重新运行自主 AI。它使用与 `ReplayPlayer` 相同的事件规范编码及快照哈希协议逐 Tick 比对，并逐行比较候选、决策、事件日志，重算汇总、检查点、动作、资源、等待原因和所有者。回放没有外部提交，不注入记录的 AI 命令。指标来自已比对的新模拟强类型事件；磁盘 `StoredReplayEvent` 只用于编码比对，不能误作强类型事件统计。

每个完成样本的输入标记最后写入，记录源码、正式内容、定义及运行时参数。独立审计严格核对这些输入。1800 Tick 探索与最终长局额外比较 54 场的 162 个观察点，见 `initial-prefix-checkpoints.json`；这不是对探索版本全部逐 Tick 数据的审计。

两次测试装配问题及旧矩阵单独归档：`pre-scene-compile-fix/` 是 PlayMode 测试误引用 Authoring 程序集时的探索版本；`pre-player-port-fixture-fix/` 是双方 AI 仍绑定玩家 HUD 端口的版本，相关场景结果为 20/21。修正只涉及测试装配：双 AI 用生产 Bootstrap 的无视图入口，其他场景继续覆盖正式玩家视图；随后重新生成完整最终矩阵并审计。失败记录不计入最终通过数。

## 判断与交付

初始对照固定参数用于识别变化来源，不构成禁止调参。根据可复现反例决定是否补候选/目标、对照评分权重或检验具体战斗参数，不预设必须改数值，也不以通过测试推定不必改数值。需要变化时另记输入版本、理由及复跑结果。本轮没有关闭前两项开关的完整消融矩阵，不能用最终结果单独计算两项改进各自的因果贡献。

`damage-weight-upper-bounds.json` 只对捕获时刻、合法应对及其他权重固定的上下文推导伤害权重上界：已记录的零伤害应对分数不随 Damage 系数改变，最差应对分数不可能高于它。因此即使 Damage 权重乘 2/4/8/16，所列攻击也不能仅靠这一项越过 Wait=0。这是评分公式的局部推导，不是多组权重的完整对局重跑，更不涵盖更改伤害、资源费用、窗口规则后的世界。

`before-task.zip/json` 保存包含任务 19、20 未提交修改的当前工作区字节；不能从 HEAD 恢复这些文件。前两项封存目录分别按 manifest 校验。本轮测试生成的旧文件先归档再恢复，最终正式内容与权重的变化显式列入 `content-changes.json`，源码及证据最终封存。

本轮 Unity 日志中的自动注入凭据参数在封存前脱敏为 `[REDACTED]`，范围见 `log-redactions.json`；不修改战斗事件、测试断言或回放数据。

使用当前项目已验证的 Unity CLI 1.0.0-beta.13 和 Unity Editor 6000.6.2f1。命令见 `verify.ps1`；复跑可能改写本轮工具输出，应在独立工作副本保存原证据。

复跑需要 PowerShell 7.6.5（含 Roslyn）、.NET 10 运行时和 Python 3；无须另装 .NET SDK。可用 `verify.ps1 -PythonExecutable <可用解释器路径>` 指定 Python，避免 WindowsApps 占位程序。本轮用 Codex 捆绑 Python。脚本依次执行原生逻辑检查、定义导出、跨运行时核对、完整生成、独立进程审计、原生场景检查和两种 Python 数据核对；旧文件恢复与最终封存使用 `evidence.py restore` / `seal`，其中 restore 依赖本轮开始前的快照，不能改用 HEAD。
