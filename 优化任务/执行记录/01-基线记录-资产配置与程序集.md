## 3. 跨资产同名局部 ID 清单与一致性结论

### 3.1 清单

### 3.2 一致性结论（诊断 S06 自动比对结果）

- 5 个局部 ID 的**标量字段（BaseTime/BaseDamage/ImpactType/StaminaCost/ForceMultiplier）跨库完全一致**；
- 各自 `Pattern` 指向不同半径版本资产（R1 vs R2，形状不同，见 §1.4）；
- 语义判定：**同名局部 ID = 「同一动作的半径变体」**，不是同一个稳定配置 ID。任务 02B 迁移时：
  1. 不得自动合并同名 ID（违反主方案 3351 行「QuickSlash 等局部同名条目不得自动合并或运行时补 ID」）；
  2. 需要显式定义 `ActionSpecId` 与半径变体/体积变体的区分方式（例如 `action.quick_slash.r1` / `action.quick_slash.r2` 或动作定义 + 参数化模式），并人工确认目标关系掩码。
- AttackPattern、UnitVolume 资产**无任何 ID 字段**——资产名与文件名是唯一标识（文件名含 `R1_0`/`R2_0` 半径后缀，由 `LibraryGenerator.RadiusSuffix` 生成），属于「依赖对象名」的缺失稳定 ID 位置。

### 5.2 关键阻塞点（02B 动工前必须解决）

1. **`Pathfinder.GridPoint` 是运行时 `Pathfinder` 类的嵌套类型**：`AttackPattern.GetAffectedTriangles(Pathfinder.GridPoint, …)`、`CombatUnit.InitialGridPosition` 直接依赖它。必须先把 `GridPoint` 抽为独立顶层类型（进共享网格程序集或 Authoring 的网格子集），否则 Authoring 会引用整个运行时 Pathfinder 类。
2. **`ImpactType` 与 `PhysicsEngine` 同文件**：PhysicsEngine 引用 CombatUnit/BattleTimeline/GameFeelManager 等大量运行时类型。迁移 enum 必须拆文件。拆分安全面：`ImpactType` 在资产中仅以 **int 值**序列化（YAML `ImpactType: 0/1/2`），无 MonoScript 引用，enum 迁移到新文件获得新 MonoScript GUID 不会破坏任何资产；PhysicsEngine.cs 留在旧程序集并保留其 .meta（guid `940d2ce0…`）。
3. **Unity 规则：自定义 asmdef 不能引用预定义程序集**（Assembly-CSharp / Assembly-CSharp-Editor 不可被引用）。因此「新建 ProjectHero.Authoring 并让新代码引用旧类型」**不存在可行方案**——闭包必须物理搬迁；旧程序集消费方（CombatUnit、PhysicsEngine、ActionScheduler、CombatArbiter、EnemyAIController、TacticsController、UIManager、Pathfinder、Intents、TimelineEditorUI、NextActionPreviewSystem、LibraryGenerator）在任务 02/02B 前按不变量 17 由暂留旧程序集的适配器读取，02B 完成闭包搬迁后整体切换。
4. **方向合法、推荐与否**：Assembly-CSharp（预定义）→ 自定义 asmdef 的引用方向**合法**，因此旧运行时代码可引用新的 Authoring/共享程序集。两个候选拓扑：
   - 候选 A（推荐）：纯网格值类型（GridDirection/TrianglePoint/GridPoint/GridMath）进入独立共享程序集（如 `ProjectHero.Grid`，可含 UnityEngine.Mathf），Authoring 与旧 Assembly-CSharp 共同单向引用；

|---|---|---|

### 6.4 无法自动推断的歧义（阻塞项清单，交 02B/08 决策）

1. **MagicResistance**：无任何使用点与资产数据 → 无法推断迁移目标（候选：映射 `elemental.*` 通道抵抗；或按 1.2 节「需要移除的设计」直接删除）。当前项目无任何元素伤害动作（5 动作全为物理三系），`elemental.fire/frost/lightning` 通道迁移时**没有旧数据可映射**。
2. **旧硬直/击倒阈值**（`impactVelocity ≥ 1.5×v_target`→Knockdown、`≥1.0×`→Stagger、`>0.5×`→推挤位移，PhysicsEngine.cs:110-138）：主方案中 `ImpactProfileId` 只决定动量生成/传递，**没有冻结旧硬直阈值到新控制模型的映射**——是 ImpactProfile 的标签/参数，还是独立规则，需 02B/08 显式决策；不得静默继承。
3. **肾上腺素获得量**（攻击者 0.1×totalDamage、受击者 0.2×totalDamage、Clash 0.5×impactDamage）：当前硬编码在伤害结算里；新规则按 `AdrenalineRules` 与 Resolution 统一量化（设计目标栏），旧系数仅作 characterization 参考。
4. 伤害数字/震屏/顿帧/弹跳（GameFeelManager、UnitBounce）与 `StatusIcon`（knockdown/stagged 图标）均为表现副作用：归事件/UnityView 消费，**不进入** DamageChannelId/ImpactProfileId 映射。
5. 事件缺失：当前无逻辑事件总线（架构师记录负责语义），因此「事件/UI 展示」栏只能映射到 GameFeelManager 直接调用点。
