## 5. A1 发现并修复的既有缺陷（1 条）

**R-A1-D1 · `ScheduleEditor.SpaceProjectionSnapshot.Restore()` 对所有动作族误用 Move 的时长公式**

- 现象：`Restore()` 无条件调用 `plan.SetPathProjection(edge, weight)`，而该 API 的语义是
  "重算 **Move** 的路径投影"（`MoveDurationTicks = weight × ResolvedBaseStepTicks`、
  `EndTick = Start + MoveDuration + Recovery`、`BudgetCostTicks = MoveDuration + Recovery`）。
  对 **Attack** 计划（`ResolvedPathWeightUnits == 0`）就变成
  `EndTick = Start + RecoveryTicks`、`BudgetCostTicks = RecoveryTicks`。
- 触发条件：**任何被拒绝的排程事务**只要其求值覆盖到一个既有攻击计划，
  该计划的 `EndTick` / `BudgetCostTicks` 就被静默改写；而窗口账本里仍持有原预留额
  （`ReservedFor(plan) == 原成本`），两者不再相等。
- 后果：该计划到期时启动门禁的 `TurnWindowBudgetAuthority.Commit` 会因
  `held != plan.BudgetCostTicks` 以 `RESOURCE_COMMIT_ERROR` 失败；同时违反
  00 号规则 28「失败事务零局部写入」与 `ActionPlanFactory`（只对 Move/Dodge 建路径投影）的口径。
- 修复（最小）：`SpaceProjectionSnapshot` 记下 `ActionType`，`Restore()` 只对
  `Move` / `Dodge` 调用 `SetPathProjection`。攻击/防御类只经 `RebindAbsoluteTicks` 复原派生字段。
- 证据：`StaleWindowCommandCannotSpendNewWindowBudget` 在修复前红（
  `oldWindow.ReservedFor(plan) = 12` vs `plan.BudgetCostTicks = 2`），修复后绿；
  既有 345 条基线用例在修复前后均全绿（该缺陷此前**零覆盖**）。

## 6. 与清单口径的两处偏离（需主理人裁定）

1. **`List<…>` 与既有测试的所有权冲突**：`RemoveEditablePlanOperation` **保留**了既有的可选
   `TerminationReason` 参数。任务包写"Remove 只携带 PlanId"，但 `Task07RemovalAndDiscardTests.cs:381`
   与 `Authoring/Task05/Task05Fixture.cs:455-457` 都在读/传该参数，二者都不在 A 流所有权内。
   A1 采取"**只新增、不删除**"：Remove 仍不携带任何请求 Tick / 锚点（即"没有排程旋钮"），
   `TerminationReason` 不构成身份、顺序或费用。**若要真正收窄到单参，需要主理人先改那两处调用点。**
2. **可空插入锚点**用 `default(ActionPlanId)` 哨兵表达（`IsValid == false` 即"无锚点"，
   `HasAnchor` 是唯一判据），**未**改成 `ActionPlanId?`。理由：`ResolveAdd` / `ValidateAnchors` /
   `ScheduleOperationIntent` 三处既有语义都按哨兵判定，改成可空是纯形式变更、收益为零而回归面变大。
