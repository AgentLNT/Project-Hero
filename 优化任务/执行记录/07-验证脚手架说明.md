## 1. 环境硬约束（踩过的坑，照抄即可）

### 1.1 必须绕过执行策略

本机 PowerShell 执行策略默认禁用脚本；`pwsh` 不存在，本机是 **Windows PowerShell 5.1**。
每次调用脚本前必须先在同一会话内放开执行策略：

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass -Force
```

### 1.2 脚本文件必须是 **UTF-8 with BOM**

PowerShell 5.1 对**无 BOM** 的 `.ps1` 按系统 ANSI 代码页解码。本脚本含中文注释，
首次以「UTF-8 无 BOM」写入时被解码成乱码，其中某个汉字的多字节序列恰好含 `0x22`（`"`），
直接导致解析失败：

```
Unexpected token '}' in expression or statement.
Unexpected token 'AUTHORING' in expression or statement.
The string is missing the terminator: ".
```

**修复方式**：写入后补 UTF-8 BOM（`EF BB BF`）。若后续有人用工具重写本脚本，必须复核 BOM 仍在，
否则会重现上述解析错误。仅含 ASCII 的脚本（如 `06-offline-harness.ps1`）不受影响。

### 1.3 相对路径必须用 `Resolve-Path` 解析（不是 `GetFullPath`）

PowerShell 5.1 里 `Set-Location` 只改 PowerShell 自己的当前位置，
`.NET` 的 `[Environment]::CurrentDirectory` 可能仍是宿主启动目录 —— 两者会不一致。
因此**不能**用 `[System.IO.Path]::GetFullPath()` 解析 `-OutDir` / `-ResultsFile`：

```
# 实测踩坑：在 %TEMP% 下用 -OutDir '.\bin'，结果
OutDir      = C:\Users\1\repos\Project Hero\bin      ← 跑到仓库上级去了，凭空建出 bin\
```

脚本内部改用 `Resolve-Path`（并递归解析尚不存在的末段目录）后：

```
OutDir      = C:\Users\1\AppData\Local\Temp\dsh-mSBsQl\t07-relcheck2\bin   ← 正确
```

保险做法：直接传绝对路径。

脚本头部把这些路径写成了常量，**换机器/换 Unity 版本必须同步修改**：

### 1.5 退出码约定

| 退出码 | 含义 |
| --- | --- |
| `0` | 全部成功（编译通过；若未加 `-CompileOnly` 则用例也全部通过） |

| `4` | 环境前置缺失（编辑器、SDK、NUnit、包缓存路径等）或其他不可预期错误 |

> 说明：当前 07 半成品同时命中「Logic 编译失败」与「Authoring 链被前置阻塞」两种情况。

### 2.5 输出格式（NUnit XML）

运行器写出的 XML 根节点形如：

```xml
<?xml version="1.0" encoding="utf-8"?>
<test-run id="1" testcasecount="147" result="Passed" total="147" passed="147"
          failed="0" skipped="0" inconclusive="0" engine="T06Runner-reflect">
  <test-case id="2" name="ProjectHero.Logic.Tests.ActionDefinitionTests.ActionPayloadKeeps..." result="Passed" duration="0.037607" />
  ...
  <test-suite type="TestFixture" id="..." name="ProjectHero.Logic.Tests.XxxTests" result="Passed" />
</test-run>
```

- `test-case` 元素带 `result`（`Passed` / `Failed` / `Skipped` / `Inconclusive`）、`duration`，
  失败时附 `<failure><message>` 与 `<stack-trace>`。
- `test-suite` 元素按夹具汇总，方便与人读结果对齐。
- 控制台同时打印一行汇总：`total=N passed=N failed=N skipped=N inconclusive=N`。

**已知格式差异（必须声明，不得当作等价物）**：
`engine` 属性固定为 `T06Runner-reflect`（运行器来自任务 06，本任务不得修改该文件），
因此**不能靠 XML 属性区分 06/07 的证据**，只能靠文件名区分（见第 5 节）。

**已知行为差异**：运行器用**子串**匹配夹具全名或方法名。若 `-Filter` 匹配不到任何用例，
它会写出一份 `testcasecount="0"`、只含夹具条目的 XML 并**返回退出码 0**。
实测（`-Filter 'Task06Commit'`，该名字只存在于 Authoring 程序集）：

```xml
<test-run id="1" testcasecount="0" result="Passed" total="0" passed="0" failed="0" skipped="0" inconclusive="0" ...>
```

**看到 `total=0` 一律视为「过滤条件写错了」，不要当成通过。** 任务 07 的提交权限用例在
Authoring 程序集里，离线跑不到，必须走 Unity（第 4 节）。

### 3.4 关键实现细节：引用集不能同时带 `UnityEditor.dll`

第一次尝试把 `<编辑器>\Editor\Data\Managed\UnityEditor.dll` **和** `Managed\UnityEngine\*.dll`

| `07-verification-playmode.xml` | 独立验证轮次 | **权威** | 同上 |
| `07-<轮次>-editmode-results.xml` | 返工轮次（如 `07-r1-`、`07-final-`） | **权威** | 与 05/06 的 `-r1-` / `-final-` 风格一致 |

规则：

1. **一轮一文件，不覆盖**：新轮次用新前缀（`-r1-`、`-final-`），保留历史便于对比回归。
2. **实现者与验证者产物必须分开命名**：`07-*-results.xml`（实现）vs `07-verification-*`（验证）。
3. **离线与 Unity 产物必须能一眼区分**：离线文件固定用 `07-logic-results.xml`，
   权威文件固定带 `editmode` / `playmode`。
4. 中间产物（DLL、`.rsp`）放 `%TEMP%\t07-harness`，**不入库**。

## 6. 权威性边界：哪些结论可离线，哪些必须 Unity

| 结论类型 | 离线脚手架 | 必须 Unity Test Runner |
| --- | --- | --- |
| `ProjectHero.Logic` 是否编译通过 | ✅ 可判定（离线即全量编译） | 需复核（Unity 用同一批源码，但引用集不同） |
| 纯 Logic 用例的通过/失败 | ⚠️ **仅过程信号**：同一批用例在编辑器 Mono + 官方 `nunit.framework` 上真实执行，可当迭代依据 | ✅ **结论以此为准** |
| `Assets/Tests/EditMode/Authoring` 是否编译通过 | ⚠️ 可选（`-AuthoringCompile`），已实测可行 | ✅ 结论以此为准 |
| Authoring 用例的通过/失败 | ❌ **不可判定**（`Resources.LoadAll` / `AssetDatabase` / 场景加载都需要 Unity 运行时） | ✅ **唯一来源** |
| PlayMode 用例 | ❌ **不可判定** | ✅ **唯一来源** |
| 「提交权限」这类状态机语义 | ⚠️ 若用例在 Logic 程序集内可离线跑；但**结论仍须 Unity 复核** | ✅ **结论以此为准** |
| 与 `Assets/**`、`.meta`、GUID、预制体/场景接线相关的任何断言 | ❌ **不可判定**（离线编译不加载资产数据库） | ✅ **唯一来源** |

**判定原则（照此写交接记录）**：

1. 离线脚手架**只允许**支撑「还没坏」这类**过程判断**，用于加速迭代。
2. 任何进入交接记录 / 独立验证记录的 pass/fail 结论，**必须**附 `07-editmode-results.xml`
   或 `07-playmode-results.xml` 这类 Unity 产物。
3. 离线结果为绿而 Unity 缺失时，只能写「离线过程信号为绿，Unity 复核未完成」，
   **不得**写成「已验证通过」。
4. 反过来，离线结果为红（如当前 Logic 编译失败）是**强证据**：源码确实编译不过，
   不必等 Unity 复核即可判定任务 07 未完成。
