### 0.1 施工中发现并修复的两个**上游既有缺陷**（必须先说明，否则无法继续）

这两处都**不是**本任务引入的，而是工作树在被交付给我时就已经存在的状态；它们的证据是文件 mtime 与 `git` 追踪状态。

**缺陷 1：工作树在交付时无法编译（CS0546）。**
- 症状：`Assets/Scripts/Logic/Commands/CommandPayloads.cs(123,22)` 与 `(134,22)`：
  `error CS0546: 'MoveEditablePlanOperation.PlanId.init': cannot override because 'ScheduleEditOperation.PlanId' does not have an overridable set accessor`（`RemoveEditablePlanOperation` 同）。
- 根因：`ScheduleEditOperation.PlanId` 被声明为**只有 get 的抽象属性**
  （`public abstract ActionPlanId PlanId { get; }`），而 `MoveEditablePlanOperation` /
  `RemoveEditablePlanOperation` 用**位置记录参数** `ActionPlanId PlanId` 继承它；
  C# 编译器为派生位置的同名声成带 `init` 访问器的覆盖属性，基类却无可覆盖的 set 访问器 ⇒ CS0546。
- 归属证据：该文件 mtime = **2026/9/23 17:12:18**（任务 03/04 施工窗口，与
  `BattleSimulation.cs` 17:06、`ActionPlan.cs` 17:11 同批），且**未被 git 追踪**
  （`git ls-files` 无此文件，属任务 03 起的新增未提交文件）。我的施工窗口是同日 22:48 之后。
  ⇒ **交付前该工作树已无法编译**；"测试基线 238/238"应当是在这批文件写入**之前**测得的。
- 修复：把两个记录改成与**同文件既有**正确写法（`ScheduleAddOperation` /
  `ScheduleMoveOperation` / `ScheduleRemoveOperation`）完全同形的
  "显式构造函数 + `public override ActionPlanId PlanId { get; }`"，
  公开构造签名（位置参数与默认值）逐字保持不变，并在 XML 文档注释里写明
  **不得改回位置记录参数**的原因。
- 影响面：仅消除编译错误，不改任何语义、不改公开 API 形态。

**缺陷 2：反应计划永远无法创建（`ACTION_PLAN_REACTION_CANNOT_REBIND`）。**
- 症状：`ActionPlan.ResolveTimingOnce` 结尾无条件调用 `RebindAbsoluteTicks(StartTick)`，
  而 `RebindAbsoluteTicks` 对反应计划显式抛
  `ActionPlanCodes.ACTION_PLAN_REACTION_CANNOT_REBIND` ⇒ **任何 Block/Dodge 计划创建即失败**。
- 根因：`ResolveTimingOnce`（任务 02 写入 `ActionPlan.cs`）没有区分普通/反应；
  而反应计划的绝对区间**只能**由 `ApplyReactionInterval()` 从固定 `TriggerTick` 推导
  （`StartTick = TriggerTick - ReactionWindupTicks`）。
- 归属证据：两处实现都是既有代码（`ActionPlan.cs` mtime 17:11），此前没有任何调用方
  （`ResolveTimingOnce` 在本次施工前**零调用点**，grep 已确认），因此该缺陷从未被暴露。
- 修复：`ResolveTimingOnce` 只在 `IsOrdinary` 时重绑；反应计划的重绑交给
  `ApplyReactionInterval()`。契约不变（"普通动作首次进入 Editable 解析相对时序；
  反应动作创建时解析并直接锁定固定 Tick"）。
- 反向验证：修复后 `ReactionPlanIsCreatedLockedWithoutEditablePhase` 与
  `ReactionPlanUsesOpportunityBindingAndNullSubmittedWindowId` 两个用例通过，
  且全量 EditMode 262/262 通过（证明没有打破任何既有行为）。

### 0.2 阶段 A 交付的契约（已冻结，阶段 B–E 必须遵守）

- **单一身份**：`ActionPlan` 是唯一形态；`ActionPlanFactory` 创建即分配稳定 `ActionPlanId`。
  普通计划创建即 `Editable`；反应计划创建即 `Locked`（`LockedAtTick = 创建 Tick`），
  **不存在可观察的 Editable 反应计划**。测试用反射断言 Logic 程序集内不存在
  `*DraftPlan*` / `*ScheduledAction*` 类型。
- **一次性时序解析**：`Attack` 的 `ResolvedWindupTicks = max(1, RoundHalfUp(BaseWindupTicks ×
  ReferenceActionSpeed / ActionSpeed))`（基准 20）；`RecoveryTicks` 恒取自 TimingSpec、
  **不随速度缩短**；`Guard` 三段（Windup/Active/Recovery）**完全不读速度**；
  `Move` 的 `ResolvedBaseStepTicks` 一次性采样，Editable 期可用 `SetPathProjection` 重算
  边数/权重，且**预算与 EndTick 用路径权重而非边数**。二次解析以
  `ACTION_PLAN_TIMING_ALREADY_RESOLVED` 稳定拒绝。
- **`ActorLane`**：按 `StartTick -> ActionPlanId` 规范排序；`IsLaneObstacle` = 固定反应区间
  或非 Editable；`IsSubmissionLocked` **只阻止新提交、绝不清除已有计划**（锁定原因以第一次为准）；
  `FindEarliestFreeStartTick` **只向右避让**；`ValidateNonOverlapping` 同时检出重叠与 Lane 内终态残留。
  ActorLane **结构上不引用** `UnitStateMachine`/`UnitState`（测试用反射逐成员断言）。
- **全局注册表**：唯一键 `ActionPlanId`；活动索引只含非终态并按 ID 升序；
  终态计划立即离开活动索引，只留 `TerminalRecordCount + TerminalDigest`（增量摘要，
  与任务 03 `HistoryDigestProtocol` 同源）；**没有按 WindowId 分桶的入口**。
- **`ActionScheduleAuthority`**：同时拥有注册表 + 全部 Lane + `ScheduleRevision`，
  只提供 `internal` 写入口（供阶段 B 事务、启动门禁与终态协调器调用）。
  `CheckNoActiveArtifactReferencesTerminalPlan()` 是可失败的不变量检查（用例含负控制）。
- **快照字段已就位**：`ActionPlanSnapshot` 现有 38 个字段（身份/投影/Guard Active/
  五类动作解析时序/路径与权重/预算与预留/创建编辑锁定 Tick/自动延期次数/终态），
  全部进入 `LogicSnapshot.ComputeHash`；`LogicSnapshot` 新增
  `TerminalPlanRecordCount` / `TerminalPlanDigest` / `NextReactionOptionSequence`，
  `ReactionOpportunitySnapshot` 新增逐选项快照（状态/截止/是否公开/结果码）。

### 18.2 冻结语义（本轮新增；接手者必须遵守）

1. **只有直接 Move 的计划可以早于旧投影**：求值器把直接操作的起点设为请求值，
   <strong>其余</strong> Editable 计划的起点一律取 `max(cursor, 当前投影起点)` ⇒ 只向右。
2. **Locked/Running/终态与固定反应区间是不可变障碍**：`EvaluateLane` 只**读**它们的 `StartTick`；
   若障碍起点落在 `cursor` 之前即以 `SCHEDULE_LANE_OVERLAP` 拒绝（结构矛盾，不静默修）。
3. **删除不左吸**：删除只从 Lane 移除目标；求值器**不**做任何左向压缩。
4. **预览与提交同源**：`preview: true` 走**完全相同的**求值路径，只是
   （a）不占用 `ActionPlanId`、（b）不注册计划、（c）不写 Lane、（d）不改修订号。
   返回的 `Evaluations` 与提交路径**逐字段相同**。
5. **Add 的 ID 归属**：候选计划按`NextActionPlanIdValue + 本批偏移`构造（**只看不占**），
   只有提交阶段才通过 `LogicIdGenerator.ReserveActionPlanId` **原子占用**。
   ⇒ **失败与预览事务不消耗任何 `ActionPlanId`**（这是本轮相对阶段 A 的一处契约收紧）。
6. **修订号**：一个成功事务恰好 `+1`；`ExpectedScheduleRevision` 与
   `BatchBaseScheduleRevision`（Step 入口冻结值）比较，**不**与本批前一事务递增后的实时值比较。
7. **批内冲突（`SCHEDULE_EDIT_CONFLICT_IN_BATCH`）**有两种触发：
   （a）同一批次内对同一计划重复 Move/Remove；
   （b）调用方经 `preClaimed`（命令处理器）声明"该计划已被本批前一事务改写"。
8. **依赖闭包 = 位置依赖 + 显式锚点的传递闭包**：`P` 依赖 `Q` 当且仅当
   `P.StartTick` 落在 `Q` **求值前**的投影区间内（半开区间），或 `P` 被锚定在 `Q` 之后；
   关系传递，且**跨过 Attack/Guard 等非移动计划**（不以"紧邻下一项"代替依赖关系）。
   闭包规模超过 `ScheduleLimits.MaxDependencyClosurePlans` ⇒
   `SCHEDULE_DEPENDENCY_CLOSURE_TOO_LARGE` 拒绝整批。
9. **`ScheduleLimits` 的真实消费（阶段 A 自曝缺口 ① 的修复）**：

| 上限 | 消费点 | 拒绝码 |
| --- | --- | --- |
| `MaxBatchOperations` | `ApplyInternal` 入口 | `SCHEDULE_BATCH_TOO_LARGE` |
| `MaxQueuedPlansPerLane` | `CheckLaneQueueLimits`（提交前，按事务后状态计数） | `SCHEDULE_LANE_QUEUE_LIMIT_EXCEEDED` |
| `MaxDependencyClosurePlans` | `ExpandPositionDependencyClosure` | `SCHEDULE_DEPENDENCY_CLOSURE_TOO_LARGE` |
| `MaxPreScheduleHorizonTicks` | `CheckHorizon`（`NewStartTick > currentTick + horizon`） | `SCHEDULE_HORIZON_EXCEEDED` |

10. **移动链路径重算端口**：`IMovementPathCalculator.Recompute(plan, newStartTick, deltaTicks)`。
    求值器在 affected ∪ `IsOrdinaryMove` 上调用它，把结果放进
    `ScheduleEvaluationResult.PathProjections`，提交时在 `RebindAbsoluteTicks` **之后**
    调用 `SetPathProjection`（因此 `EndTick` / `BudgetCostTicks` / 预留都用新路径权重）。
    默认实现是 **fail-closed 的** `NotImplementedMovementPathCalculator`（返回 null = 不重算），
    **不得**把恒等实现当作"任务 06 已完成"。

### 19.2 冻结语义（本轮新增）

1. **门禁四分结果的判定顺序**（先永久、后临时）：
   不变量前置（非 Editable 普通计划 / 未到期 / 反应计划）→ 所有者死亡 → PrimaryTarget 关系/存活
   → 有限临时阻塞（控制状态 / 限时空间）→ 无有限恢复或延期越限 → `Startable`。
2. **`RetryAtTick` 必须是有限且严格大于当前 Tick 的值**。没有有限恢复边界时（例如授权不可用）
   **不是** `Retryable`，而是 `Terminal(ActorUnavailableAtStart)` ——
   任务包禁止"下一 Tick 再试"的无限轮询。
3. **`InvariantViolation` 不是终态**：内部矛盾必须以稳定码令 `Step` 失败，
   **不得**"终止计划后继续"。Step 里对它的处理是 `throw new LogicDefinitionException(code, detail)`。
4. **原子提交**：`CommitStart` 先经端口消费预留、再在同一处写
   `State = Running` + `LockedAtTick = tick`；端口失败时恢复全部计划字段并抛
   `SCHEDULE_START_GATE_COMMIT_INCONSISTENT` ⇒ **不存在 Locked-but-not-Running**。
5. **系统延期复用同一求值器**：`ScheduleEditor.ApplySystemAutoDeferral` 调用
   `_evaluator.Evaluate`（与命令事务同一个 `ScheduleEvaluator` 实例），
   仅动 `AutomaticDeferralCount + 1` 与 `ScheduleRevision + 1`，
   **不**改 `LastRequestedStartTick`，**不**消费预留。
6. **终态协调器**
   - 第一次请求胜出：已是终态 ⇒ 幂等返回，不覆盖状态/原因/`TerminalTick`、不重复清理；
   - `EnterTerminal(plan, None, tick)` 语义 = 自然完成（`Completed`、无原因）；
   - `EnterTerminal(plan, reason, tick)` 语义 = 带原因的 `Terminated`；
   - 固定清理顺序 = `(Order, ParticipantId)` 的 `Ordinal` 序（**与装配顺序无关**）；
   - 终态同时清 `ReservedTurnBudgetTicks`（释放未消费预留）并**不改** `ScheduleRevision`；
   - 本 Tick 的终态候选进 `FrozenTickCandidates`（按 `ActionPlanId` 去重），
     在阶段 19 交给归档端口**冻结一次**。
7. **归档端口**：`ActionPlanTerminalArchiveSource` 用
   `HistoryRecordKind.ActionPlanTerminal` + `ActionPlanRegistry.StableKeyOf(plan)` +
   `ArchivedAtTick = plan.TerminalTick` + `HistorySealProof.Sealed`，
   **载荷为 `null`** —— 这是刻意的：`ActionPlanRegistry.MarkTerminal` 也用 `null` 载荷，
   因此 `LogicSnapshot.TerminalPlanDigest` 与 `HistoryArchive.Summary` 的增量摘要**同源**。
   改成规范字节载荷会改变历史摘要，属于一次显式 `ReplayFormat.Version` 变更，**不属于任务 05**。

## 24.3 冻结语义（本轮新增；接手者必须遵守）

1. **公开时机**：`TryOpenForTelegraph` 只接受 `IsOrdinary && ActionType == Attack && !IsEditable`；
   `TelegraphTick` 首版 = 来源 `StartTick`；仍为 Editable 的攻击**结构上无法**公开机会。
2. **资格**：`Reactable` 标签 + `ImpactTick - TelegraphTick >= MinimumReactionLeadTicks`
   （取值来自 `BattleDefinition.ReactionRules`，未硬编码）。
3. **候选**：`PrimaryTargetOnly` ⇒ 固定主目标；`AllTargetsInArea` ⇒
   `IAreaThreatCandidateSource`（默认 `NoAreaThreatCandidateSource`，**fail-closed**，
   真实几何属于任务 06）。两者**都**只经
   `IFactionRelationResolver.Allows(attack.AllowedTargetRelations, …)` 过滤，并排除来源自身与未知/死亡单位。
   本系统在**结构上**不读 `IsPlayerControlled`、Controller 类型或任何"默认敌方"标志
   （用例用反射逐成员守这条）。
4. **选项**：按 `ActionSpecId` Ordinal 排序；`ResponseDeadlineTick = ImpactTick - 反应前摇`；
   Block 只在"来源有可格挡伤害分量**或**动量非零"时提供，Dodge 只在 `Dodgeable` 时提供；
   动作集合归属只在防御者声明了 ActionSet 且可解析时生效（与创建期同口径）。
5. **公开门槛**：只有 `ResponseDeadlineTick >= TelegraphTick + CommandIngressLeadTicks` 的选项进入
   机会；没有公开选项的候选**不创建机会**，全部候选都不行时返回
   `REACTION_NO_REACHABLE_OPTION`（不写任何状态）。
6. **接受**：`tick > ResponseDeadlineTick` 才 `OPTION_DEADLINE_ELAPSED`（**含端点**：
   等于截止 Tick 仍可接受）；判定顺序为
   机会存在 → 防御者匹配 → 仍 Open → 选项存在 → 已公开 → 未解析 → 未过期 → 来源未终态 →
   动作类型 → Lane 未锁 → 资源接缝 → 固定区间 → 创建。
7. **计划形态**：一律经 `ReactionPlanner` → `ActionPlanFactory.TryCreateReaction`，
   因此**直接 Locked**、`SubmittedWindowId = null`、`BudgetCostTicks = 0`、
   `StartTick = TriggerTick - 前摇`、`EndTick = TriggerTick + 后摇`；接受**不**推进 `ScheduleRevision`。
8. **固定区间不可平移**：Lane 重叠以 `REACTION_LANE_INTERVAL_OCCUPIED` 稳定拒绝，
   障碍**绝不被抢占**，也不重排任何普通计划。
9. **过期**：`tick > ResponseDeadlineTick` 才对**每个**选项发一次
   `ReactionOptionExpiredEvent`；最后一个开放选项过期时以 `AllOptionsExpired` 关闭机会。
   第一次离开 `Open` 只发一次 `ReactionOpportunityClosedEvent`；离开后既不再发关闭事件，
   也不再接收命令（`OPPORTUNITY_NOT_OPEN`）。
10. **`SourceThreatCancelled`**：关闭机会、经**统一终态协调器**以该原因终止绑定反应，
    并**发出释放未消费预留的通知**。未注入接收方时请求进 `PendingReservationReleases`
    **排队保留**（绝不静默丢弃），任务 07 装配后取走。**其他反应终态不触发**该例外。
11. **Dodge 触发接缝**：`Accepted -> Triggered` **只能**由 `ConfirmTrigger` 完成
    （重复确认幂等）。生成反应 Intent ≠ 实际触发；本任务**不伪造触发**，
    `ReactionTriggeredEvent` 只在确认接缝成功之后发射一次。
12. **事件发射**：`EventSink`（接到 `LogicEventOutbox.Emit`）为可选；
    未注入时事件留在 `EmittedEvents` 缓冲供测试/审计。`ActionPlanAutoDeferredEvent`
    携带阻塞原因码 / 旧新 `StartTick` / `RetryAtTick` / 次数 / 稳定 ripple `PlanId` 列表 / 提交后修订号。

## 26.4 `RequestedStartBeforeCommandTargetTickRejectsWholeBatch` 的最小产品补口

阶段 B/C 的编辑器此前**只**检查 `RequestedStartTick < 0`，没有检查"起点早于命令目标 Tick"：
这样的计划永远到不了自己的到期门禁（阶段 7 只处理 `StartTick == tick`），会在 Lane 里退化成

以新稳定码 `SCHEDULE_START_TICK_BEFORE_COMMAND_TICK` **整批拒绝**（`ResolveMove` 因此新增
`currentTick` 形参）。正/负控制见 `Task05SimulationWiringTests.RequestedStartBeforeCommandTargetTickRejectsWholeBatch`。

## 27.1 R1（D2，中危）`ReactionOpportunityId` 双分配器 —— **已修复**

### 27.1.1 采纳的裁定：让契约分配器成为唯一来源（"首选"方案）

两条候选路径中**采纳第一条**（"让契约分配器成为唯一来源"），理由如下：

1. **任务 03 冻结契约已经指定了归属**。`03-交接记录.md:211` 明文规定实例 ID 的来源与快照字段：
   `ReactionOpportunityId` 属于 `UnitId / ActionPlanId / ReactionOpportunityId / WindowId / EffectId`
   这一族，由 `LogicIdGenerator` 分配，快照字段名为 `NextReactionOpportunityId`；
   `03-确定性内核.md:83` 也把 `NextReactionOpportunityId` 列为任务 03 **先冻结接口**的字段。
   第二条路径（"删除契约同名分配器"）会**替换任务 03 已冻结的契约条目**，
   使 `ReactionOpportunityId` 成为五种实例 ID 里唯一的例外，并让任务 03 的
   `ReactionOpportunityIdsHaveIndependentMonotonicGenerator` / `RuntimeIdsStartAtOneAndAreNeverReused`
   / `SequenceCountersAreIndependentFromObjectIds` 三条冻结用例失去对应的生产机制。
2. **与同类 ID 的现行结构完全同形**。`UnitId` 经 `NextUnitId()`、`ActionPlanId` 经
   `NextActionPlanId()`（+ 提交点 `ReserveActionPlanId`）、`WindowId` 经 `NextWindowId()`、
   `EffectId` 经 `NextEffectId()`——**全部**由 `LogicIdGenerator` 分配，且**各只有一个分配方法**。
   让 `ReactionOpportunityId` 回到同一矩阵，不需要任何新模式，也不需要新增接口。
3. **旧计数器的语义已被验证为"零调用死计数器"**。`LogicIdGenerator._nextReactionOpportunityId`
   在生产路径上从未被推进（恒为 1），快照里"`NextReactionOpportunityId == NextReactionOptionSequence`"
   只是"前者被后者喂养"的巧合，不是两个分配器真的一致；保留它仍是**两个可各自取号的路径**。
4. **不改任何冻结快照字段名**。`LogicSnapshot.NextReactionOpportunityId` 与
   `LogicSnapshot.NextReactionOptionSequence` 两个字段**全部保留**（两者都进入 `ComputeHash`，
   见 `LogicSnapshot.cs:604` 与 `:713`），因此哈希字段集合、`LogicSnapshot` 构造函数签名、
   `ShadowComparisonDetector` 的既有比较通道、PlayMode 的 `CopySnapshot` 夹具**逐字不变**——
   零基线扰动。

### 27.1.6 排查过程中的一次**夹具自伤**（如实披露）
