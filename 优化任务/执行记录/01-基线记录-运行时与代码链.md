## 6. 典型战斗片段（任务包产出 2，静态推导）

> 通用前提：两单位属性相同（Str=Dex=Con=Wis=Int=10、ArmorWeight=10、ArmorDefense=0）→ **TotalMass=90、Swiftness=10、MaxHealth=200、MaxStamina=100、MaxFocus=5**（CombatUnit.cs:85-97）。运行时 `Start()` 会把 CurrentHealth/Stamina 重置为 200/100（CombatUnit.cs:154-155）。Player 用 ForRadius1 库与 Radius_1 体积，Enemy 用 ForRadius2 库与 Radius_2 体积。默认场景两单位相距 10 格（(-5,-5) vs (5,5)），首帧任何攻击都打不到——以下片段 A/B 使用等价局部坐标并**标注推导**；默认站位下的真实流程是 AI 先移动（EnemyAIController.FindBestPositionNearTarget maxRings=3，:199-256）再攻击。

### 片段 A —— 攻击命中（QuickSlash，相邻单位）

- 确定输入（推导用等价局部坐标，待运行时验证标注）：Player 位于 (0,0) 朝东（Facing=East）；Enemy 位于 (2,0) 朝东。玩家选中 Player → 点 Quick Slash → 点击 Enemy 侧地面 → 时间线放在 +0s。`TacticsController.HandleGroundClick`（:476-517）→ `ScheduleAttack(timeline, player, quickSlash, startDelay=0, dir)`。
- 时间线事件（ActionScheduler.ScheduleAttack :36-63）：T=0 `StateChangeIntent("Windup", 1.0s)`（P50，扣体力 10，SetIsActing，ForceFacing）；T=1.0s 同 Tick 依 Priority 序执行：`StateChangeIntent("Recovery",0.5s)`(P50) → `AttackIntent`(P0)；T=1.5s `StateChangeIntent("Idle")`。
- 命中判定：AttackIntent.ExecuteSuccess（:35-92）→ `Pattern_Slash_R1_0.GetAffectedTriangles((0,0), East)` 绝对三角形含 (3,0,±1)、(4,±1,∓1)、(2,±1,∓1)；`GridManager.GetUnitsInArea` 查占位 → Enemy（Radius_2 体积含 (3,0,±1) 等）→ **命中**。
- 数值链（PhysicsEngine.ResolveCollision :88-139）：Kw(Slash)=0.6；动量=90×10×0.6×0.8=**432**；impactVelocity=432/90=**4.8**；护甲减伤=0/(0+100)=0 → physicalDamage=15；impactDamage=432×0.02=**8.64**；totalDamage=**23.64**。阈值：4.8 ≤ 0.5×10=5 → **无击退、无硬直、无击倒**（:135-137，pushDistance=0）。结果：Enemy HP 200→176.36；Player 肾上腺素 +2.364、Enemy +4.728（上限 100，:99-102）；`OnImpact` 无 knockback 分支。
- 观察点：Enemy HP=176.36、双方 CurrentStamina（Player 90）、`Debug.Log "[Physics] ... Damage: 23.6 | ImpactV: 4.8"`、T=1.5s 后 Player 恢复 Idle（InWindup/InRecovery 时序经 `GetActionProgress(CurrentTick)` 可在 UnitStatusHUD 动作环观测）。**待运行时验证**：命中判定与视觉位置分支（AttackIntent.cs:73-86 读 `UnitMovement.IsMoving`）在本片段未触发；HashSet 目标遍历顺序（单目标时无影响）。

### 片段 B —— 移动/位置变化（混合 1/2 权重路径）

- 确定输入：玩家选中 Player → Move → 点击 (-4,-2) 顶点（世界坐标经 `WorldToGrid` 取整到偶校验格，GridManager.cs:228-250）→ 时间线放在 +0s。

- 时长（ActionScheduler.EstimateMoveDuration :22-34，Swiftness=10）：边 1 时长 `clamp(1/(10×0.1),0.2,4.0)=1.0s`；边 2 时长 `clamp(2/1.0)=2.0s`；总时长 **3.0s**（时间线块 DurationSeconds=3.0，TimelineEditorUI 量子化 0.05s 不变）。

### 片段 C —— 死亡与战斗结束

- 确定输入（推导）：Player 与 Enemy 相邻（同片段 A 站位），Player 连续 3 次 HeavySmash（ForRadius1：BaseTime 1.5 / Damage 40 / Blunt / FM 1.6 / Stamina 25，均命中且每次命中前 Enemy 已被击倒或跟随）：每次 totalDamage=68.8（详见 §10 夹具 F1），3×68.8=206.4 ≥ 200 → 第 3 次命中时 `CurrentHealth<=0`。
- 死亡路径（CombatUnit.OnImpact :216-227）：`timeline.CancelEvents(this)`（释放该单位全部未来事件与 Commit 预留，BattleTimeline.cs:143-154）→ `UnregisterOccupancy/UnregisterUnit` → `gameObject.SetActive(false)`。
- 胜负路径（BattleManager.Update → CheckWinCondition :36-61）：下一帧轮询 `FindObjectsByType<CombatUnit>` → enemyAlive=false → `EndBattle("VICTORY…")` → `_battleEnded=true`、`Time.timeScale=0.2`。**注意（characterization）**：EndBattle **不清空时间线**、不暂停 Timeline——0.2× 慢速下时间线继续推进，AI 也继续行动（EnemyAIController 只检查 `Timeline.Paused`，:65）；仅 BattleManager 自身停止胜负轮询。R 键 `RestartGame` 重载场景（:72-77）。
- 观察点：Enemy GameObject active=false；Console 两条 Log（"has been DEFEATED!" / "Battle Ended: VICTORY…"）；全屏 GUI 文字；timeScale=0.2。**待运行时验证**：CombatDemo.Update 与 BattleManager.Update 的脚本执行顺序（两脚本在不同 GO，顺序未配置）→ 胜负判定相对 Tick 推进的帧偏移；同帧多 Tick 推进时胜负观察粒度；第 2、3 次 HeavySmash 之间的 AI 干预（AI 行为随机，见 §2.4）——**真实场景无法用活 AI 复现确定性输入，建议由任务 03B 隐藏场景固定输入脚本替代**。

## 8. 旧 CombatArbiter 能力边界（任务包产出 5）

全部定位：Core/Interactions/CombatArbiter.cs。

1. **仅两两处理**：`Resolve` 双重循环 `for i / for j=i+1`（:22-42），遇交互即 `processed.Add(a); processed.Add(b)`（:38-39），后续任何包含 a 或 b 的对直接 `continue`（:29）——三方互相攻击时，第三方的接触/Clash **被静默丢弃**，结果依赖输入顺序。
2. **动量无方向、标量相减**：Clash 分支 `float p1 = CalculateMomentum(...); float p2 = ...; float residual = p1 - p2;`（:86-95），`residual>0` 败者是 b、否则败者是 a——**默认相向**假设（没有方向字段可比较）。
3. **处理一对后立即修改取消状态**：`atk1.Cancel(); atk2.Cancel();`（:92-93）在计算同时发生；Parry `pAtk.Cancel(); pDef.Cancel();`（:114-115）；Dodge `dAtk.Cancel()`（:127）；Intercept `iMov.Cancel()`（:141）。取消即修改 `IsCancelled` 布尔（CombatIntent.cs:25-28），并影响 `BattleTimeline.ProcessTick` 的执行阶段（BattleTimeline.cs:191-197）。
4. 其他边界：Clash 双方各 `CurrentFocus += 1`（:89-90）；败者经 `PhysicsEngine.ApplyClashResult` 吃剩余动量伤害（:98-103），**Clash 路径不做硬直/击倒判定**（ApplyClashResult 无阈值分支，PhysicsEngine.cs:29-41）；Parry/Dodge **取消整个攻击意图**（AOE 其他目标一起免伤）；Intercept 使移动者 `IsKnockedDown=true`（:143）且**不清理该单位剩余移动事件**（§12）；Escape 用 `eAtk.IgnoreTarget(eMov.Owner)`（:157）做目标级豁免——这是旧代码里唯一的目标级机制；`IsTargeting` 读取的是**当前** GridPosition/Facing（:186），非意图产生时的快照。
5. 交互判定顺序固定：Clash → Parry → Dodge → Intercept(hitsEnd) → Escape(hitsStart && !hitsEnd)（:47-70）——同 Tick 多种关系时按此序短路。
6. `ExecuteInterruption`（MoveIntent.cs:73-81、PlanMoveIntent.cs:65-70、PlanFacingIntent.cs:31-34 覆写）**从未被调用**（grep 验证：无调用点）→ 中断清理逻辑是死代码；真实中断路径的副作用（视觉 snap、取消剩余事件、Reservation 释放）不发生在 Intercept/Parry/Dodge 上。

**以上全部是 characterization baseline，不是新多方规则必须保持的不变量。** 新协议（主方案 0.4.2-0.4.6）要求：冲突图、同组同 Tick 全量动量同时求解、`OppositionFactorQ10` 有向损耗、动作级终态统一提交、目标聚合与同时强制位移。
