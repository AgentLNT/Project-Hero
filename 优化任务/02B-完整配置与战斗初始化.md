# 02B - 完整配置、ID 迁移与战斗初始化

状态：待执行  
前置任务：01、02  
建议规模：3-6 天

## 执行目标

把任务 02 的单条兼容切片扩展为完整、可验证的真实项目配置链。任务结束时，所有当前战斗使用的 ActionLibrary、AttackPattern、UnitVolume、单位定义、动作集合与 Encounter 配置都能无歧义地转换为一个纯 C# `BattleDefinition`；战斗初始化器能从该定义、初始 RNG 种子和显式注入的运行时资源创建确定的初始逻辑世界、闭合 `FactionModelDefinition` / 唯一关系解析器、`EncounterSlotId -> (UnitId, FactionId)` 映射及不可伪造的 `ControllerId -> UnitId 集合` 控制关系。阵营归属、阵营关系、控制权和胜负目标必须是正交数据。

本任务也是创建 `ProjectHero.Authoring` asmdef 的唯一默认入口。只有把读取旧资产所需的完整类型依赖闭包一并迁入 Authoring 后，才能创建该 asmdef；不得让 `ProjectHero.Authoring` 反向引用预定义 `Assembly-CSharp`，也不得复制一套同名旧类型绕开引用规则。

任务 03 可以使用本任务产出的真实 `BattleDefinition` fixture 建立内核；任务 10 只负责调用已经完成的构建和初始化接口，不再现场补 ID、猜默认值或重新实现一套配置转换。

## 最终依赖方向

```text
Assembly-CSharp（尚未迁移的兼容代码） ──→ ProjectHero.Authoring ──→ ProjectHero.Logic
                                      └──────────────────────────→ ProjectHero.Logic

ProjectHero.Logic.Tests ──→ ProjectHero.Logic
ProjectHero.Authoring.Tests ──→ ProjectHero.Authoring / ProjectHero.Logic
```

`ProjectHero.Authoring` 可以引用 UnityEngine 和 `ProjectHero.Logic`，但不得引用 `Assembly-CSharp`。如果任务 02 的闭包清单显示某个转换器仍需要 `Assembly-CSharp` 类型，必须先搬迁该类型及其必要依赖或把转换器继续留在旧兼容层；不能创建非法引用后把编译失败交给任务 10。

## 必须产出

1. 创建 `ProjectHero.Authoring` asmdef 及其 EditMode 测试程序集；迁入读取旧配置所需的完整依赖闭包，保留脚本与资产 `.meta`，并扫描场景、Prefab 和 ScriptableObject 引用。
2. 定义完整、纯 C#、不可变的 `BattleDefinition`，至少包含：
   - 规则版本、TicksPerSecond 和参与哈希的 `BattleRules`，包括后续门禁使用的非负 `MaxAutomaticDeferralsPerPlan`、最大排程视野，以及 `PathCostRules` / 首版固定 `PathSearchRules(MaxExpandedNodes: 4096, MaxPathWeightUnits: 256, MaxPathEdges: 192)`。三项以 `<=` 为合法边界，只有严格大于才失败；不定义独立 `MaxSearchDistance`，Encounter `GridBoundary` 是唯一空间搜索边界。任务 01 的真实 Encounter 测量只用于记录余量和性能基线，不得覆盖这些常量；也不得直接复制旧代码的 `1000` 次或 `±100` 坐标保护。
   - 全量 `UnitDefinition`、`ActionSpec`、`AttackPatternSpec`、`MovementPatternSpec`、`VolumeSpec`、`ActionSetDefinition`、`DamageChannelDefinition`、`ImpactProfileDefinition` 和 `StatusEffectSpec`（当前没有的类型允许为空集合）；每个 Attack Payload 显式携带非空且只含已定义位的 `AllowedTargetRelations`。每个带朝向的 Pattern/Volume 必须是按 `GridDirection 0 -> 11` 排列的完整规范整数表，Logic 定义中不得保留需要运行时求值的旋转配方。
   - 稳定 `FactionId` / `FactionDefinition`，以及 `FactionModelDefinition` 中每两个不同阵营恰好一条、按 ID 规范排序的静态对称 `FactionDisposition(Allied/Neutral/Hostile)`；同 Faction 的不同 Unit 固定 Allied，同一 Unit 固定 Self。每个 `EncounterUnitSlot` 显式携带 FactionId，不能从 Controller、玩家标志或单位定义猜测。
   - 一个明确的 `EncounterDefinition`：稳定 Encounter ID、规范化 `GridBoundaryDefinition`、出场槽位、初始位置/朝向、单位定义引用，以及 `VictoryDefinition` 的非空、互斥 Allied/Hostile FactionId 目标集合与显式 Victory/Defeat/Draw ResultCode。边界必须能稳定枚举/查询合法 doubled-coordinate GridPoint，并包含全部初始占位；Allied 组内部必须在关系矩阵中互为 Allied、跨组必须 Hostile；Hostile 组内部不附加关系约束。未列入两组的目标外阵营不参与消灭条件，但仍保留关系矩阵中的目标资格，不能统一当作 Neutral。
   - 稳定 `ControllerId`、`CommandSourceKind` 和 `ControllerBinding`：每个玩家/AI Controller 显式绑定可控 `EncounterSlotId`；重复 Controller、歧义控制关系、悬空槽位和外部 `System` 来源必须拒绝。该来源类型将由后续命令网关派生优先级，不能由命令载荷覆盖。
   - 并发行动的权威 `ConcurrentActionDefinition`（至少包含 `MetaResourceCost`）进入定义与哈希；本场初始局外资源数值通过 `BattleRuntimeInputs` 显式注入。费用不得由命令载荷、调用方参数或外部 Singleton 提供。
   - 高阶反应的权威 `ReactionRules`、`AdrenalineRules`、Block/Dodge 肾上腺素费用、ReactionWindup/Recovery、`Reactable/Blockable/Dodgeable` 标签及成功 Block/Dodge 奖励进入定义与哈希；两种成功奖励分别小于所有对应动作费用，费用不超过个人周期上限。Attack/Guard/Move 的肾上腺素费用必须为 0，Guard 合格动作抵抗必须严格为部分值 `[1,1023]`，Block 合格抵抗由规则固定为 1024。
3. 建立显式旧 ID 迁移清单：
   - 现有诸如 `QuickSlash` 的局部 ID 不能直接当作全局 `ActionSpecId`。
   - 迁移键可以在 Authoring/Editor 边界使用“资产 GUID + 局部条目 ID”定位旧条目，但最终 Logic ID 必须是人工确认的稳定小写字符串，运行时不得依赖 GUID。
   - 同名条目只有在规范化定义完全一致且迁移清单明确声明共享时才能共用一个 Logic ID；Pattern、数值或语义不同则必须映射为不同 ID。
4. 实现完整 `BattleDefinitionBuilder`：
   - 扫描或接收显式列出的全部相关资产。
   - 执行 ID 格式、重复、缺失引用、循环引用、非法数值、Tick 量化、动作时序、PathCost/PathSearch 规则、Encounter 网格边界、Faction 引用/关系矩阵、TargetRelationMask 和 Victory 分组校验。
   - 对 N 个 Faction 要求恰好 `N*(N-1)/2` 个规范无序关系对；拒绝缺失、重复、A-B/B-A 反向重复、自关系、悬空 Faction 或非法枚举值，不得用 Hostile/Neutral 默认值补洞。
   - 为上述失败冻结 `FACTION_RELATION_MISSING`、`FACTION_RELATION_DUPLICATE`、`FACTION_RELATION_NOT_CANONICAL`、`FACTION_RELATION_UNKNOWN_ID`、`TARGET_RELATION_MASK_INVALID` 与 `VICTORY_FACTION_RELATION_CONFLICT`；错误列表也按稳定键排序。
   - 拒绝 Attack 的目标关系掩码为空或包含未知位；旧资产必须逐项迁移为显式掩码，当前普通敌对攻击可配置 Hostile-only，但不能在 Logic 端硬编码该默认。
   - 拒绝槽位缺少/引用未知 Faction、Victory 阵营集合为空/重叠/悬空、Allied 组内部非 Allied、跨组非 Hostile 或结果码为空；Hostile 组内部关系不得被目标分组覆盖。ControllerBinding 与 Faction 分组不要求同构，不能把“玩家控制”等同于 Allied。
   - 所有集合使用稳定顺序；改变 Unity 资产发现顺序不得改变定义、错误列表或哈希。
   - 对每个旧 AttackPattern/UnitVolume 读取 East 与 EastNorth 两套基准，并使用主方案 2.3.1 的受检 60° 整数公式各展开六次，交错生成 12 向最终表；每向按 `(X,Y,T)` 去重并排序。`T` 非 `-1/1`、`X+Y+T` 为奇数、基准缺失、运算溢出、最终方向不完整或显式旧方向与生成结果不一致时整体拒绝，不得回退 `GridMath.Rotate` 或用偶数基准猜测奇数方向。
   - 为方向几何失败冻结 `DIRECTIONAL_BASE_MISSING`、`TRIANGLE_POINT_INVALID`、`DIRECTIONAL_EXPANSION_OVERFLOW`、`DIRECTIONAL_TABLE_INCOMPLETE` 和 `DIRECTIONAL_EXPLICIT_DATA_MISMATCH`；错误列表继续按稳定键排序。
   - 校验 `PathCostRules` 恰好声明偶数方向权重 1、奇数方向权重 2，启发函数/开放集规则版本受支持，三个搜索上限均为正且覆盖当前 Encounter 的签字基线。冻结 `PATH_COST_RULE_INVALID`、`PATH_SEARCH_RULE_INVALID` 与 `GRID_BOUNDARY_INVALID`；不得给 `MoveSpeed` 建立路径成本系数。
   - 任一被当前 Encounter 引用的配置无法转换时，整体构建失败并给出稳定、可定位的错误；不得跳过后继续运行。
   - 显式迁移旧 `ImpactType` 的双重语义：为伤害生成稳定 `DamageChannelId`，为动量生成独立 `ImpactProfileId`；旧 Armor/Magic 防御映射到明确通道。任何无法确认的类型或折叠字段必须阻止构建并进入迁移报告，不得猜测成通用物理伤害。
   - 校验每个可反应攻击有足够 `MinimumReactionLeadTicks`，否则必须显式标为 `Unreactable`；校验每个 Block/Dodge 都位于至少一个单位的 ActionSet 中且费用/标签闭合。ActionSet 不因单位由玩家或 AI 控制而采用不同规则结构。
5. 实现规范化 `BattleDefinitionHash` 输入：
   - 哈希覆盖全部会影响玩法结果的定义、规则常量和显式初始配置，包括规范化 Pattern/Volume 12 向最终表、`GridDirection` 数值/方向顺序、`PathCostRules`、启发函数/开放集平局规则、`PathSearchRules`、Encounter 合法网格边界、规范化 Faction 关系矩阵、每个攻击的 AllowedTargetRelations、Victory 分组与动态生成阵营策略。
   - 显示名、Asset 路径、导入顺序、资产内点的原始排列、对象地址和 Builder 实现细节不参与哈希，除非它们本身被明确声明为玩法数据。Builder 实现变化但最终规范表逐点相同时，定义哈希必须保持不变。
6. 实现纯数据战斗初始化入口，例如：

   ```csharp
   BattleInitializationResult BuildInitialState(
       BattleDefinition definition,
       EncounterDefinitionId encounterId,
       BattleRuntimeInputs runtimeInputs);
   ```

   `BattleRuntimeInputs` 必须显式携带初始 RNG 种子和本场需要的局外资源输入。初始化器按 `EncounterSlotId` 的 `StringComparer.Ordinal` 顺序分配初始 `UnitId`，把槽位 FactionId 原样复制进运行时单位，创建不可变 `FactionRelationResolver`、全部初始单位、资源和注册表，将 `ControllerBinding` 映射为只读 `ControllerId -> UnitId 集合`，并返回 `EncounterSlotId -> UnitId` 映射。首版单位 FactionId 创建后不可变；动态生成只能从权威生成定义的固定 FactionId 或显式 `InheritSourceFaction` 策略解析，并把结果写入创建事件/快照。Controller/来源绑定来自已验证定义而非命令；不得读取 GameObject 名、场景注册顺序、`IsPlayerControlled`、`GetInstanceID()` 或运行时随机 GUID 来推断阵营。
7. 全项目配置转换报告，写入 `优化任务/执行记录/02B-配置迁移记录.md`，至少列出：
   - 发现和成功转换的每类资产数量。
   - 旧 ID → 新稳定 ID 映射。
   - 同名冲突、缺失引用、非法值及处理结果。
   - 尚未被任何 Encounter 使用但仍保留的资产。
   - 主战斗 Encounter 的定义哈希和初始化复现步骤。
   - 旧伤害/冲击字段 → `DamageChannelId` / `ImpactProfileId` / 防御通道的逐项映射，以及所有人工确认项。
   - 每个 AttackPattern/UnitVolume 的 East/EastNorth 基准来源、12 向展开结果摘要、规范化前后点数、显式旧方向校验结果及任何被拒绝坐标；确认当前资产与旧查询输出逐方向一致。
   - 当前 Encounter 的合法网格边界、典型/最大 ExpandedNodes、EdgeCount、PathWeightUnits，相对固定 `4096 / 256 / 192` 上限的余量，以及为何不沿用旧 `1000`/`±100` 保护的结论。
   - 各单位 ActionSet 中 Guard/Move/Block/Dodge 的可用性；若某单位没有高阶反应，必须是内容配置结果而不是玩家/敌人硬编码。
   - 每个 EncounterSlot 的 FactionId、规范化 Faction 关系对、每个 Attack 的 AllowedTargetRelations、动态生成阵营策略、VictoryDefinition 的 Allied/Hostile/ResultCode 映射，以及旧玩家/敌人标志如何仅作为人工迁移线索而不再参与关系或胜负。
8. 为任务 03 提供至少一个来自真实资产的最小 `BattleDefinition` fixture；为任务 10 提供只读构建 API、初始化 API 和槽位绑定映射，后续任务不得重新解释旧资产。

## ID 迁移规则

- 配置 ID 必须满足主方案的小写英文字母、数字、点和下划线规则。
- 不允许用 `ToLowerInvariant()` 自动把旧 ID 当成最终 ID；大小写修正不能解决跨库同名但定义不同的问题。
- 旧资产 GUID 只用于迁移清单定位，不进入 Logic 类型、Replay 或运行时快照。
- 一个最终 ID 只能对应一个规范化定义；发现同 ID 不同内容时以 `DEFINITION_ID_CONTENT_CONFLICT` 稳定失败。
- 所有引用必须指向最终强类型 ID，不保留字符串名称回退查询。

示例：

```text
ForRadius1.asset + QuickSlash → action.quick_slash.radius_1
ForRadius2.asset + QuickSlash → action.quick_slash.radius_2
```

这只是命名示例，最终 ID 由项目设计确认；实现者不得自行根据文件名批量生成后直接提交。

## 工作步骤

1. 使用任务 01/02 的清单确认旧 Authoring 类型和资产引用闭包，先制定搬迁表，再移动脚本或创建 asmdef。
2. 创建 Authoring asmdef；每次移动一组闭包后立即编译并检查 Missing Script、丢失资产引用和循环依赖。
3. 建立显式 ID 迁移清单，对全部动作库、Pattern、Volume、单位和 Encounter 运行预检，先暴露冲突再实现转换。
4. 完成全量转换器、交叉引用解析、Pattern/Volume 受检整数展开、定义规范化和哈希；对当前全部相关资产逐方向比较新规范表与旧实现输出，只允许将“结果相同”列为已批准差异，任何点集变化必须先作为玩法变更评审。
5. 完成战斗初始化入口与槽位映射。
6. 对所有当前 Encounter 运行批量转换和初始化测试，并至少对主战斗场景执行一次不启动战斗逻辑的构建/绑定冒烟检查。
7. 写入配置迁移记录，列出任何仍需任务 10 处理的纯场景绑定工作；不得把配置语义缺失转交给任务 10。

- `QuickSlash` 等跨库同名条目不会因自动小写或最后写入覆盖而合并。
- `BattleDefinitionBuilder` 对全项目当前配置给出零错误结果；任何警告都有明确保留理由并记录。
- 当前全部 AttackPattern/UnitVolume 均由两套合法基准生成完整规范 12 向表，并逐方向证明与旧实现的当前资产输出一致；缺失/非法数据不能通过运行时 fallback 继续。Logic 定义、初始化结果与哈希只携带最终整数表，不携带三角函数、浮点舍入或旧旋转配方。
- `BattleDefinition` 明确携带偶数/奇数方向 1/2 路径权重、启发函数/平局版本、正的搜索上限与 Encounter 合法网格边界；取值可追溯到任务 01 的测量和设计签字，MoveSpeed 不参与选路。
- 相同资产内容以不同发现顺序输入时，规范化定义、错误顺序和 `BattleDefinitionHash` 完全一致。
- 同一 `BattleDefinition`、Encounter、RNG 种子和运行时输入重复初始化 100 次，初始单位、槽位映射、资源、ID 下一个值和初始快照完全一致。
- Controller/来源/可控单位关系包含在规范化定义与哈希中；调用方不能在战斗启动后临时扩大控制范围或伪装为 `System` 来源。
- 每个槽位和运行时单位都有显式稳定且首版不可变的 FactionId；不同阵营的每个无序对都恰有一个静态对称关系，同 Unit/Same Faction/跨 Faction 的关系查询符合冻结规则。Faction 矩阵、Attack 目标关系掩码、动态生成阵营策略和 Victory 数据进入规范化定义与哈希，控制器类型或可控关系变化不会隐式改变目标资格或胜负分组。
- 所有当前伤害字段都被显式归入伤害通道、冲击 Profile、被动抵抗或被记录为已移除；不存在运行时仍依赖旧 `ImpactType` / 通用 `DamageReduction` 的模糊链。
- ReactionRules、反应动作、攻击标签和所有单位 ActionSet 构成闭合定义；玩家与 AI 的控制类型不会改变同一单位理论可用的动作。
- 任务 03 可以直接使用真实定义 fixture，不需构造另一套测试专用配置模型。
- 任务 10 可以从场景的稳定 Encounter/Slot 绑定调用现成构建与初始化 API，不需读取旧动作名称、补默认值或现场生成配置 ID。

## 禁止事项

- 不让自定义 asmdef 引用预定义 `Assembly-CSharp`。
- 不复制旧 ScriptableObject 类型或 Logic 定义以伪造可编译边界。
- 不从显示名、文件名、资源加载顺序、GameObject 名或运行时实例 ID 自动生成最终 Logic ID。
- 不静默合并跨库同名配置，不以“最后加载者获胜”解决冲突。
- 不跳过无法转换但被 Encounter 引用的资产。
- 不在 Logic 运行时调用旧 `GridMath.Rotate`，不在 Builder 中用 `Mathf.Sin/Cos` 或浮点舍入生成权威 Pattern/Volume 表，也不在缺少 East/EastNorth 基准时猜测方向。
- 不把旧 Pathfinder 的浮点 `g/f`、`maxIterations = 1000` 或距起点 `±100` 窗口当作未声明默认值；不允许 Authoring 用单位速度改写路径边权。
- 不用“缺失即 Hostile/Neutral”、Controller 类型、玩家标志、名称、Tag 或 Layer 填补 Faction 关系；不把目标外阵营强制改写为 Neutral。
- 不允许命令、View 或 Controller 提供/修改运行时 FactionId；动态生成只接受已验证定义解析结果。
- 不在本任务实现 `BattleSimulation.Step()`、动作排程、窗口、仲裁或表现反馈。
- 不把完整配置转换或默认值解释留给任务 10。
