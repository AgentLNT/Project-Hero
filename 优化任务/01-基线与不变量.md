# 01 - 基线、清单与不变量测试

状态：待执行  
前置任务：无  
建议规模：1-2 天

## 执行目标

在改变架构前建立可复核基线：确认当前战斗入口、状态写入点、Unity 依赖、典型场景行为和未来必须保持的设计不变量。该任务的产物是后续重构的比较依据，不实现新时间线、窗口或资源系统。

## 必读范围

- 主方案：核心目标、`0.1-0.5`、`1.3`、`3.11.1`、第一阶段路线、风险与注意事项
- [00 - 执行规则与依赖](00-执行规则与依赖.md)
- 当前 `Assets/Scripts/Core/`、`Assets/Scripts/UI/`、`Assets/Scripts/Visuals/` 中所有会写入战斗状态的入口

## 必须产出

1. 在 `优化任务/执行记录/01-基线记录.md` 记录：
   - Unity 版本与测试方式。
   - 现有战斗入口、`Update()` / `LateUpdate()` 中的逻辑写入点，并分类为“顶层时钟/Timeline 推进者”“Legacy 从属写入者”“只读输入/表现回调”；每项记录场景/Prefab 对象路径、时间来源、调用目标和写入对象。
   - 单列 `CombatDemo.Update() -> BattleTimeline.AdvanceTime(Time.deltaTime)` 的主场景启动链，以及 `CombatUnit.Update()`、`BattleManager.Update()`、`EnemyAIController.Update()` 等已知旧逻辑回调，供任务 03B 建立模式门控。
   - `UnityEngine` 依赖、Singleton、`FindObjectsByType` 与热路径 `GetComponent` 清单。
   - 当前动作、Intent、网格、状态、AI、胜负与表现调用的责任归属。
   - 当前配置和运行对象使用的标识来源，特别记录对象名、注册顺序、`Time.frameCount`、`GetInstanceID()` 和缺失稳定 ID 的位置。
   - 全部当前战斗使用的 `ActionLibrarySO`、`AttackPattern`、`UnitVolume`、单位/动作集合与 Encounter 的数量、引用关系和消费场景；单独列出 `QuickSlash` 一类跨资产同名局部 ID 及其内容是否一致。
   - 当前脚本所属程序集、asmdef 引用图，以及把旧配置类型迁入 `ProjectHero.Authoring` 所需的完整类型依赖闭包；不得只记录目标目录。
   - 用户已有未提交改动及本任务如何避让。
2. 记录 2-3 个当前可运行的典型战斗片段，至少覆盖：攻击命中、移动或位置变化、死亡或战斗结束。
3. 把连续时间轴五条不变量转成命名明确的验收用例清单；当前基础设施允许时直接自动化，否则保存确定的输入、观察点和预期，交由任务 02/03 启用。
4. 记录当前编译结果、Console 错误和可重复的场景启动步骤。
5. 明确记录旧 `CombatArbiter` 的能力边界：仅两两处理、动量无方向、默认相向标量相减、处理一对后立即修改取消状态；这些是 characterization baseline，不是新多方规则必须保持的不变量。
6. 为至少一条可复现攻击记录旧 `PhysicsEngine` 的完整数值链：`TotalMass`、`Swiftness`、`ImpactType`、`ForceMultiplier`、传递动量、`BaseDamage`、护甲减伤率、普通冲击伤害、总伤害、`impactVelocity`、硬直/击倒判定和位移格数；另记录一条 Clash 剩余动量冲击伤害。该夹具是任务 08 量化兼容的数值依据。
7. 为至少一条旧 `ActionScheduler` 攻击记录时序输入、中间值和边界：旧实现实际使用 `BaseTime * 20 / max(1, Swiftness)` 作为前摇，命中发生在前摇结束时，后摇固定 `0.5` 秒。该记录是 characterization baseline；新方案的权威契约是把旧 `BaseTime` 作为 `BaseWindupSeconds` 导入，以 `ReferenceActionSpeed = 20`、`RoundHalfUp` 和默认 `RecoveryTicks = 30` 在普通计划首次进入 Editable 时一次性量化相对时长，不能把旧调度器的 `max(1, Swiftness)` 兼容保护或浮点排程本身当作未来规则来源。
8. 建立旧计划终态写入与从属对象清理地图：列出自然完成、取消、目标失效、Clash/移动交互、控制、死亡和战斗结束的所有入口，以及每个入口当前是否清理 ActionPlan 活动索引、Lane、Intent、MovementSegment 和 Reservation。把“仅战斗结束清完整、普通终态可能残留”的位置明确标为待替换风险，不将该旧行为写成兼容目标。
9. 单独记录当前 Block、Dodge、Move 的时序来源、费用、状态区间、命中/免伤判断、玩家/AI 可用性门槛与肾上腺素清零点；这些是待替换基线，不能升级为新规则。
10. 盘点当前所有“伤害类型”来源：`ImpactType`、物理/魔法减伤、攻击资产字段、伤害调用参数与事件/UI 展示。标明哪些字段实际控制动量、哪些控制伤害、哪些被折叠或未使用，为任务 02/02B 的 `DamageChannelId + ImpactProfileId` 显式迁移表提供证据。
11. 单独盘点旧时间线编辑器的交互与重算语义，并逐项定位到代码和可复现操作：指定未来起点、关键帧/整数 Tick 吸附、删除、拖动重定位、Lane 内重排、重叠时向右 ripple、Move 链预测起止位置/路径/步数/时长重算，以及删除后是否自动左吸。把“应保留的玩家能力”与“旧 UI 直接改写可变对象的实现方式”分栏；新方案保留前者，后者由 ScheduleEditCommand 替换。
12. 建立旧“敌我/友军/中立”判定地图：逐项列出 `IsPlayerControlled`、EnemyAI 固定目标、Controller 类型、GameObject Tag/Layer、名称、场景引用和胜负布尔值的读取点，并标明它分别影响命令目标、AOE 候选、反应机会、AI、占位还是胜负。逐个当前 Attack 记录实际可影响关系，作为任务 02B 人工填写 `AllowedTargetRelations` 与 Faction 关系矩阵的迁移证据；不能把旧二元玩家/敌人行为直接升级为完整模型。
13. 单独记录旧 `Pathfinder` / `ActionScheduler` 的移动数值链：12 个方向的坐标增量、偶数方向 cost/distance 1、奇数方向 cost/distance 2、启发函数、同 `f` 首发现行为、`maxIterations = 1000`、距起点 `±100` 坐标窗口，以及 `EstimateMoveDuration` 对 `Swiftness` 的逐边 Clamp。至少采集一条同时含权重 1/2 边的真实路径，记录路径权重、逐边旧时长与总时长；另对当前全部 Encounter 测量典型/最大 ExpandedNodes、EdgeCount、PathWeightUnits 和合法网格边界，用于验证首版固定上限 `4096 / 256 / 192` 的余量并建立性能基线。旧保护值只作为 characterization，不自动升级为新规则；测量结果也不得在实现阶段静默改写已冻结上限。

## 工作步骤

1. 检查 Git 状态与 Unity 项目版本，确认主战斗场景和启动入口。
2. 使用源码搜索建立“状态写入地图”、配置引用图和程序集依赖图，不要仅按目录名称推断职责。
3. 运行当前项目和可用测试，捕获典型片段的输入、关键状态与结果。
4. 为以下未来测试拟定固定名称和预期：

   - `ThreeWayClashUsesAllOriginalMomentaSimultaneously`
   - `EqualOppositeImpulsesCancelKnockbackButNotDamageOrImpact`
   - `AreaAttackKeepsHitsOnTargetsThatDidNotBlockOrDodge`
   - `GuardPartiallyReducesDamageAndMomentumOnlyWhileActive`
   - `BlockCannotBePlannedBeforeReactionOpportunityExists`

## 允许改动

- `优化任务/执行记录/01-基线记录.md`
- 为采集基线而新增的最小测试夹具或只读诊断代码
- 必要时对现有代码增加不改变行为的测试接缝

默认不得修改战斗规则、资源数值、动作顺序、场景对象或资产定义。

## 验收标准

- 基线记录中的每个结论都能定位到文件、类型、运行结果或复现步骤。
- 至少 2 个典型片段有确定输入和可比较输出。
- 五条核心不变量均有对应测试名称、前置状态、操作和预期结果。
- 旧二体标量仲裁与新多体有向目标被明确分栏记录，未把旧系统的能力限制误写为新规则。
- 旧动量、普通伤害、Clash 剩余伤害与控制阈值至少各有一组可代入复算的输入、公式中间值和期望输出。
- 攻击时序夹具明确记录 `BaseTime`、`Swiftness`、前摇结束/命中时刻和固定后摇；同时另列新规则在给定 `BaseWindupSeconds`、`ActionSpeed` 与 `StartTick` 下的预期 `ResolvedWindupTicks`、`ImpactTick`、`RecoveryTicks`、`EndTick` 和 `BudgetCostTicks`，不混淆旧实现证据与新设计契约。
- Block/Dodge/Move 基线能定位当前 Tick/秒来源、状态免伤、资源费用、玩家特例与 AI 缺口；新目标另列 Guard/Move 普通时序、ReactionOpportunity 绑定时序和通用单位权限，二者不混写。
- 寻路基线明确证明项目已有偶数/奇数方向 1/2 权重，且 `Swiftness` 只在选路后影响逐边时长；真实场景报告包含 ExpandedNodes、EdgeCount、PathWeightUnits、边界与旧失败条件，并验证首版固定上限 `4096 / 256 / 192` 的实际余量，同时与旧 `1000`/`±100` 保护分栏。
- 敌我盘点覆盖命令、AOE、反应、AI、占位和胜负的全部旧入口；每个当前攻击都有可复核的目标关系迁移结论，未知处标为阻塞配置迁移而非补默认 Hostile。
- 伤害盘点能给出旧字段到 `DamageChannelId`、`ImpactProfileId`、被动抵抗和标签的显式候选映射，并列出无法自动推断的歧义。
- 终态写入地图能定位每个直接状态修改和局部清理入口，并逐项列出可能遗留的活动索引、Intent、MovementSegment、Reservation 或 EndTick 位置提交。
- 时间线编辑基线能逐项证明旧版未来放置、吸附、删除、重定位、向右避让与移动链重算的真实行为，并明确删除是否左吸；不得以“新 UI 尚未实现”为由把这些既有玩家能力从迁移清单删除。
- Unity 回调清单能够区分顶层时钟推进、Legacy 从属写入与只读输入/表现；主场景/Prefab 对象路径及启停条件完整，任务 03B 无需重新猜测所有权。
- 当前战斗配置清单能追溯到资产与消费场景；跨库同名 ID、缺失稳定 ID和悬空引用被明确列出，不以自动小写或文件名推断为已解决。
- Authoring 依赖闭包能说明每个待搬迁类型、直接依赖、引用者和 `.meta` 保留要求，并明确当前不存在可行的自定义 asmdef → `Assembly-CSharp` 引用方案。
- 明确列出当前无法自动化的原因，不使用跳过测试冒充覆盖。
- Git 差异只包含基线与最小测试接缝，没有玩法改动。

## 禁止事项

- 不创建新的 `TurnWindowManager`、`ActionPlan` 或 `BattleSimulation` 实现。
- 不删除旧 bool、Singleton 或 Unity 表现调用。
- 不因为旧行为与新方案不同而修改主方案。
- 不做全仓格式化或批量命名空间调整。

## 交接重点

后续任务需要知道：当前可运行入口、顶层时钟推进链、Legacy 从属写入组与只读输入/表现回调分类、对应场景/Prefab 路径、可复用的场景夹具、最危险的状态写入点、全部计划终态与局部清理入口、完整配置/旧 ID/场景引用清单、旧敌我判断入口与逐 Attack 目标关系迁移表、旧 1/2 路径成本/移动时长链及真实搜索规模、Authoring 依赖闭包与程序集拆分会遇到的循环依赖，以及哪些设计目标尚未具备可执行测试。
