# 00 - 执行规则与依赖

## 用途

本目录把《Project Hero 游戏架构优化方案》拆成可交给单个 agent 闭环执行的任务包。主方案继续作为架构事实来源；任务包只定义施工顺序、改动边界、验收证据与交接格式，不另立一套战斗模型。

执行任一任务前，agent 必须完整阅读：

1. [主优化方案](../优化方案-逻辑表现解耦与逻辑帧判定.md)
2. 本执行总则
3. 当前任务包
4. 当前任务包列出的前置任务交接结果与相关源码

## 冲突处理优先级

若文档、旧代码与任务描述互相冲突，按以下顺序处理：

1. 主方案“〇、游戏设计基准”，尤其是 `0.2.1 连续时间轴的五条核心不变量`
2. 主方案“架构原则”、`2.2 稳定 ID 与 Sequence 规则`与 `BattleSimulation.Step()` 阶段顺序
3. 本执行总则
4. 当前任务包
5. 旧代码的既有实现与命名

不得为了复用旧代码而改写高优先级规则。遇到无法兼容的冲突时，停止扩大改动，记录冲突位置、可选方案和影响，交回调度者决定。

## 全任务强制不变量

以下规则在每个任务中都成立：

1. 所有进入权威排程的 `ActionPlan` 默认跨回合窗口存在；窗口切换不得取消、截断、加速、锁定、结算或重排计划。只有显式 `ScheduleEditCommand`，或到期计划执行前门禁触发的确定性系统自动延期事务，可以修改仍为 `Editable` 的普通计划。
2. `TurnWindow` 只控制提交新动作的权限和预算，不拥有动作，也不是动作执行或结算边界。
3. `ActionPlan` 生命周期独立于 `TurnWindow`；普通计划使用同一对象按 `Editable -> Locked -> Running -> Completed/Terminated` 演进，`SubmittedWindowId` 仅用于预算来源与审计；反应计划记录 `ReactionOpportunityId` / `SourceThreatPlanId`、`SubmittedWindowId` 为空，并在接受后直接 Locked。
4. `ActorLane` 与权威 ScheduleEditor 是普通计划能否接受和编辑的唯一排程来源；`ActionStartGate` 是普通计划原子锁定/启动的唯一入口，`ReactionPlanner` 是固定反应创建为 Locked 的唯一入口。`UnitStateMachine` 只描述当前状态和有限阻塞边界，不能替代 Lane/排程/门禁判断。
5. 仲裁读取本 Tick 全部有效动作及其逻辑空间关系，不按提交窗口过滤；过去窗口提交的动作可与当前及未来窗口动作交互。
6. 所有影响战斗结果的时间均使用整数 Tick；秒只在配置导入和 UI 展示边界出现。
7. 所有战斗状态修改只发生在 `BattleSimulation.Step()` 的固定阶段内。
8. `ProjectHero.Logic` 不引用 `UnityEngine`；表现层只能消费事件和只读快照，不能写回逻辑对象。
9. 影响结果的集合遍历、命令、Intent、Resolution、事件和 ID 必须有稳定顺序。
10. 逻辑事件描述战斗事实，不携带震屏、顿帧、动画时长等表现策略。
11. 战斗结束 Tick 必须通过唯一 Finalizer 闭合全部活动计划、Intent、MovementSegment、Reservation、Lane、窗口和授权；结束后的 `Step()` 是不推进任何逻辑状态的幂等 `AlreadyEnded` 返回。
12. 多方仲裁必须使用离散有向整数动量，从只读快照构建冲突图并统一求解；接触级失效、动作级中断和目标聚合不得混用 pairwise 即时状态修改。
13. 首版攻击采用“速度修正前摇 → 命中 → 固定后摇”：`ActionSpeed` 只在普通计划首次进入 Editable 时量化一次相对前摇，命中只发生在 `ImpactTick`，后摇不受速度缩短，预算成本等于解析后的前摇加后摇；排程编辑可重绑绝对 Tick，但不得因后续属性变化重新采样相对时长。
14. `Guard` 是窗口型普通防御，只在 Active 半开区间提供部分伤害抵抗与部分动量抵抗；`Block` / `Dodge` 是消耗肾上腺素、绑定已公开攻击机会的高阶反应，只有一个由来源 `ImpactTick` 推导的 TriggerTick。Block 对该 Tick 全部合格接触完全抵抗；Dodge 先原子换格并从新位置复核接触；三者都不得通过状态布尔值实现区间无敌。
15. Reservation 冲突服从规范化命令处理顺序；先成功提交者持有预留，后处理命令只回滚自身事务，不得按独立优先级抢占已提交资源。
16. 配置定义使用受约束的稳定字符串 ID；战斗实例使用从 1 开始、单场单调递增且不复用的强类型 `long` ID；Sequence 与对象 ID 分开命名。所有下一个 ID/Sequence 值进入规范化快照与哈希，禁止使用 GameObject 名、注册顺序、`GetInstanceID()`、对象地址或运行时随机 GUID；进入快照不等于首版必须支持中途恢复。
17. 程序集迁移必须服从可编译的单向依赖：任务 02 只建立 Logic/Logic.Tests，读取旧 `Assembly-CSharp` 类型的适配器暂留旧程序集；只有任务 02B 搬迁完整 Authoring 依赖闭包后才能创建 `ProjectHero.Authoring`；任务 10 最后搬迁表现依赖闭包并创建 UnityView。Bootstrap、适配器契约和 New Driver 搬入 UnityView 时，待回切的 Legacy 具体适配器继续留在 `Assembly-CSharp`，实现 UnityView 拥有的接口并通过显式槽位注入；UnityView 不得反向引用 Legacy 类型。完整 `BattleDefinition`、全资产 ID 迁移和战斗初始化通过前，后续任务不得用测试夹具替代真实配置链并宣称可接入场景。
18. 命令生产者只能提交 `CommandRequest`，不得声明 `ControllerId`、来源优先级、`ProducerOrdinal`、`CommandSequence`、规则费用或反应触发 Tick。已注册入口绑定 Controller/来源并分配生产者序号；Logic 网关按派生优先级、`ControllerId` Ordinal 和生产者序号规范化，整组拒绝重复/回退键，再生成全局唯一命令序号。排程编辑必须验证 `ScheduleEditScope(ExpectedScheduleRevision, ExpectedWindowId?)`，新增/增加预算时窗口必填；反应命令必须验证 `ReactionCommandScope(ReactionOpportunityId)`；费用均从权威定义读取。
19. `ActionPlan` 的自然完成、排程删除、目标失效、来源威胁取消、交互/控制打断、强制位移破坏旧起点或 Reservation、Owner 死亡和战斗结束必须经唯一且幂等的终态协调器；每个 Step 返回时，活动计划索引、Lane、Intent、MovementSegment、Reservation 和资源预留不得引用终态计划。已冻结进本 Tick 冲突图的 Intent 先完成该 Tick 求解；Editable 普通计划终态释放尚未消费的窗口预算预留，Locked 后不退款；清理不回卷 ID/Sequence、不撤销已提交结果，也不自动前移后续计划。反应预留仍只有来源攻击在 TriggerTick 前取消且 Cycle 匹配时返还。
20. 首版回放是从 Tick 0 重演的开发者工具；`LogicSnapshot` 是覆盖所有未来影响状态的规范化观察/哈希模型，不是可用于 `Restore()` 的完整 `SimulationState`。中途存档/恢复、任意跳转、周期性完整状态检查点和玩家回放产品不属于本任务链。
21. 每个战斗场景只能有一个 `BattleRuntimeBootstrap` 拥有战斗时钟/Timeline 的顶层 Unity `Update()` 调度权；Legacy 适配器、Shadow runner 与 `UnityBattleDriver` 都只能被调用，不得形成第二个自主时钟入口。迁移期旧逻辑 `Update()` 必须登记为 Legacy 从属写入者并由 Bootstrap 按模式整体门控：只在 Legacy/Shadow 启用，在 New 全部禁用。UI/视觉回调可保留，但不得写逻辑；任一时刻恰有一个权威写入路径。
22. Shadow 新模拟必须使用独立逻辑世界，只能消费镜像输入并输出比较报告；不得绑定 View、修改 Unity 或旧逻辑状态、播放反馈或决定场景胜负。推进发生在 Bootstrap 的 `Update()`，比较只发生在同一 Bootstrap 显式排序的只读 `LateUpdate()` 检查点；规则必须区分基础设施一致性、新规则不变量、限期清零的暂不可比较字段与逐用例批准差异，禁止按帧索引猜测配对或用宽泛忽略列表制造假绿。
23. `Legacy` / `Shadow` / `New` 模式必须在创建本场战斗前固定，战斗中不得热切换或迁移运行中状态。Legacy 不调用新 Step，New 不调用旧 `BattleTimeline.AdvanceTime()`，Shadow 只有 Legacy 写权威状态；任务 11 完成重新开局式回切演练、稳定性验证和引用扫描前不得删除 Legacy 启动路径。
24. 每条攻击接触必须携带分通道 `DamageComponents[]` 与独立 `MomentumPacket`。`DamageChannelId`、`ImpactProfileId`、伤害标签、被动抵抗、动作抵抗和动量抵抗不得重新合并为单一 `ImpactType` / `DamageReduction`。
25. `ReactionOpportunity` 只能在来源 AttackPlan 于执行 Tick 锁定、启动并公开后生成；Editable 计划不得泄露为威胁。控制者不能预填 BlockTick/EvadeTick。`TriggerTick = SourceAttack.ImpactTick`，命令晚于派生 StartTick 时稳定拒绝，固定反应区间不能由 ActorLane 或时间线编辑器平移。
26. 高阶反应权限不得检查 `IsPlayerControlled`。任意单位是否可 Block/Dodge 只取决于 ActionSet、有效机会、Controller 控制权、状态/Lane、标签、目的格和可用肾上腺素；AI 与玩家必须提交同一种 ReactionCommand。
27. 肾上腺素 Available 跨其他单位窗口保留，在反应接受时转为带个人 CycleId 的计划预留、TriggerTick 消费；该单位下一次自身窗口打开时递增 Cycle 并清零 Available，但既有预留继续履约且旧周期取消不得返还到新周期。窗口关闭不得清零，预留量不得重复消费。获得量只按本 Tick 已提交的最终伤害/成功结果规范聚合一次并受 `MaxAvailablePerCycle` 限制；成功 Block/Dodge 奖励都必须小于对应动作费用。
28. 普通时间线不建立独立草稿对象或整窗口提交阶段。完成 Tick N 后锁定线显示 N+1；Step N+1 必须先按 CommandSequence 原子应用目标 N+1 的 ScheduleEdit，再评估 StartTick=N+1 的普通计划。ExpectedScheduleRevision 与该 Step 冻结的 BatchBase 比较；同批不相交 Lane 可依序成功，重叠依赖后处理者拒绝。编辑只触及 Editable 普通计划；自动重排只向右避让，删除不左吸，移动链的路径/位置/时长/预算/Reservation 依赖闭包同时重算。每个成功命令事务令全局 ScheduleRevision 恰好 +1，失败事务零局部写入。
29. 到期 Editable 普通计划必须经闭合 `ActionStartGate`：Startable 原子完成冻结、TurnBudget `Reserved -> Spent`、`Locked -> Running`；带有限 `RetryAtTick` 的临时状态/空间阻塞复用同一 `ScheduleEvaluator` 原子向右延期，保持 Editable/Reserved 并令 ScheduleRevision 恰好 +1；无有限恢复、次数/视野超限或永久目标/路径失效经统一协调器终止并释放未消费预留。`MaxAutomaticDeferralsPerPlan` 版本化；Locked/Running/反应不重排，固定反应控制失败按 `InterruptedByControl` 终止且不退款，内部 Lane/状态矛盾必须明确报不变量错误。
30. `FactionModelDefinition` 必须以规范化无序对完整声明每两个不同阵营之间静态、对称的 Allied/Neutral/Hostile 关系；同 Faction 的不同单位为 Allied，同一 Unit 为 Self。Attack 必须显式声明非空 `AllowedTargetRelations`，命令、PrimaryTarget、AOE、ReactionOpportunity 和 AI 共用唯一关系解析器；不得从 Controller、玩家标志、名称、Tag 或缺省值猜测敌我。
31. `EncounterUnitSlot` 和运行时单位必须携带稳定且首版不可变的 `FactionId`；动态生成只能从权威定义解析固定/显式继承阵营，`ControllerBinding` 只定义控制权。消灭型胜负只读取 `VictoryDefinition` 的非空、互斥 Allied/Hostile 目标集合，并验证 Allied 组内部互为 Allied、跨组互为 Hostile；Hostile 组内部关系保持矩阵原值。目标外阵营不阻止消灭条件，但仍保留关系矩阵中的目标资格。双方同 Tick 全灭使用显式 DrawResultCode；不得读取 `IsPlayerControlled`、Controller 来源或窗口归属推断结果。
32. 三角格寻路必须沿用版本化 `PathCostRules`：偶数 `GridDirection` 边权 1、奇数方向边权 2；`MoveSpeed` 不参与选路，只量化每权重单位 Tick。A*、MovementSegment 时长和 TurnBudget 必须共用 `PathWeightUnits`。首版 `PathSearchRules` 固定为 `MaxExpandedNodes = 4096`、`MaxPathWeightUnits = 256`、`MaxPathEdges = 192`；三项均以 `<=` 为合法边界，只在严格大于时失败，不设置独立坐标距离上限，搜索空间由 Encounter `GridBoundary` 唯一限定。启发函数、规范平局、检查位置、失败优先级、合法网格边界、上述搜索上限和 checked 溢出规则都进入 `RulesVersion` / `BattleDefinitionHash`，不得沿用旧 `Pathfinder` 的浮点分数、隐式 `1000` 次或 `±100` 坐标保护作为未声明默认值。
33. 强制位移必须跨本 Tick 全部冲突组形成一个全局请求批次，在不可变 LogicGrid 快照和临时占位空间中逐格同时求解，最终只经 `ApplyBatchRelocation` 一次提交。它不得调用 Pathfinder、普通 Move、MovementSegment 或普通 Reservation 仲裁；边界/障碍停在最后合法格，静止单位阻挡，同落点、footprint 重叠、交换和循环均无赢家，只允许依赖链最终通向空格的独立请求同时腾挪，且不隐式连锁推人。强制位移优先于 Reservation：按 ActionPlanId 经统一终态协调器终止受影响空间计划、释放未来 Segment/Reservation 后批量换位；同 Tick 死亡在换位及事件之后处理。输入排列不得改变位置、停止原因、失效计划、事件或哈希。

## 工期口径

各任务顶部的“建议规模”表示：前置接口已经冻结、交接产物可用且没有新增玩法时，完成当前任务主要编码与直接验证所需的**净实施工作量**。它不是从项目开始到任务交付的日历工期，默认不包含：

- 等待前置任务、接口评审和跨任务交接。
- Unity 场景、Prefab、序列化引用和旧兼容层暴露出的额外修复。
- 全量回归、试玩反馈、性能回退调查和预期外返工。
- 团队沟通、排期空档及风险缓冲。

主方案的 **12-16 周** 是单人全职完成全部迁移的整体日历估算，已经包含跨任务集成、可编辑时间线迁移、场景修复、回归和缓冲，因此不能用各任务建议天数的简单相加替代。

任务 03B 的唯一运行时所有者、三模式壳、隐藏验证场景和最小 Shadow 报告建议规模为 **2-4 天**。它不是任务 10 的驱动原型预付款：交付时主场景必须已经通过 Bootstrap 以 Legacy 模式运行，旧 `CombatDemo` 不再自主推进，且 Shadow 零写入证据可复核。

任务 10 属于高不确定性的集成与切换任务，按“New 驱动补全与模式切换 2-4 天”加“场景、可编辑时间线、UI、表现迁移与回归 5-8 天”估算，总建议规模为 **7-12 天**。若任务 01 发现多个主战斗场景、复杂 Prefab 继承或大量序列化旧引用，调度者应在任务 10 开始前再次上调，而不是压缩验收范围。

任务 02B 的 **3-6 天** 包含 Authoring 依赖闭包搬迁、全资产 ID 映射、完整定义构建和初始化验证，不得把这些工作隐藏到任务 10 的场景迁移工期中。若配置扫描发现跨库同名冲突、缺失稳定 ID 或大量序列化引用，必须先滚动上调 02B，而不是在任务 10 运行时生成临时 ID。

每个任务交接都应记录实际投入、偏差原因和剩余集成工作；调度者据此滚动修订后续估算。

## 单任务执行流程

每个 agent 必须按以下流程工作：

1. 检查 `git status --short`，区分已有用户改动与本任务改动，不覆盖无关变更。
2. 阅读任务要求和相关实现，先确认现有类型、场景引用与编译边界，再改代码。
3. 为任务列出短计划；实施过程中保持任一时刻只有一个明确的进行中步骤。
4. 先补失败测试或可复核夹具，再完成最小实现；不得用空断言或跳过标记伪造通过。
5. 每次改动保持可编译；兼容壳只能转发，不能形成第二套权威状态。
6. 运行当前任务测试、所有已完成前置任务的回归测试，以及与改动相关的场景检查。
7. 从任务 04 起，凡改动已接入模拟的子系统，都要扩展并重跑任务 03B 的隐藏场景/Shadow 比较配置；不能只跑 EditMode 测试后把集成风险推迟到任务 10。
8. 检查差异中是否混入无关格式化、资源重写或用户文件。
9. 按交接模板报告结果。变更集大小应接近一个可审查提交，但是否创建提交由调度者另行决定。

## 文件与改动边界

- “允许改动”是默认所有权范围；为修复直接编译错误可以做最小跨界调整，但必须在交接中逐项说明。
- 不得顺手迁移后续任务、批量重命名无关文件或重写场景资源。
- 不得删除旧字段或旧组件，除非当前任务明确要求且已完成引用扫描与场景验证。
- 新增逻辑代码优先进入 `Assets/Scripts/Logic/`。任务 02 中读取旧类型的最小配置适配器暂留 `Assets/Scripts/Core/Compatibility/Authoring/` 或等价的 `Assembly-CSharp` 目录；任务 02B 搬迁完整依赖闭包后，正式配置转换进入 `Assets/Scripts/Authoring/`。任务 03B 的 Bootstrap、模式、Legacy/New 调用适配器与 Shadow runner 暂留 `Assets/Scripts/Core/Compatibility/Runtime/` 或等价的 `Assembly-CSharp` 目录，隐藏验证场景及其 PlayMode 测试属于该任务边界；任务 10 创建 UnityView 后，Bootstrap、适配器契约和 New/Shadow 实现保留 `.meta` 搬入 `Assets/Scripts/UnityView/`，Legacy 具体适配器留在旧程序集并通过 UnityView 拥有的接口注入，直至任务 11 删除。不得让自定义 asmdef 引用 `Assembly-CSharp`。
- 纯逻辑测试默认进入 `Assets/Tests/EditMode/`，由 Unity EditMode Test Runner 执行且不加载战斗场景；只有场景、Prefab、MonoBehaviour、输入和表现桥接测试进入 `Assets/Tests/PlayMode/`。两类测试都必须遵守程序集依赖方向。
- 本轮任务不要求建立独立 SDK 风格的 `.NET` 测试工程；以后若需要无 Unity CI、服务器模拟或独立战斗工具，再作为单独任务评估，不能为此复制一份 Logic 源码。
- Unity 生成的 `.meta` 文件必须与对应资源一并保留；不得修改当前任务之外的现有 `.meta`。

## 通用完成定义

一个任务只有同时满足以下条件才算完成：

- 当前任务的必需行为、拒绝路径和边界条件都有自动化测试或明确的可复核证据。
- 所有已完成任务的测试仍通过；Unity 项目无新增编译错误。
- 未违反全部强制不变量，尤其没有把窗口重新变成动作容器或结算边界、没有绕过启动门禁或留下 Locked-but-not-Running 普通计划、没有让系统自动延期移动不可变计划/无限重试/漏记修订、没有用控制权或缺省值代替 Faction 关系/胜负、没有让排程编辑重采样既有计划的属性时长或越过锁定边界、没有让普通或战斗终态留下仍可执行的从属对象/资源预留、没有把 Guard/Block/Dodge 退化为状态区间无敌、没有让生产者预填反应 Tick、没有建立非法 asmdef 依赖或用测试配置冒充真实初始化链，没有退化为 pairwise 即时仲裁或引入不稳定 ID，没有把强制位移逐单位提交、复用普通移动/寻路/Reservation 竞争或按稳定键选冲突赢家，没有把命令身份、顺序或费用交给生产者自报，没有把规范化快照误当成首版恢复存档，也没有多运行时推进所有者、Shadow 写回或 New 模式调用旧 Timeline。
- 新增公共类型、排序键、时间区间和拒绝原因均有明确语义。
- 没有遗留两套同时写入的权威状态。
- 交接中列出改动文件、测试命令与结果、未验证项、后续任务所需接口。

## 必须停止并交回的情况

- 继续实现需要改变五条连续时间轴不变量。
- 任务要求与主方案的资源、时间区间、阶段顺序或提交授权语义冲突。
- 用户已有改动与当前任务修改同一逻辑且无法安全合并。
- 必须扩大到两个以上后续任务才能获得“看似可用”的结果。
- 无法证明场景只有一个顶层运行时推进所有者、New 已禁用全部登记的 Legacy 从属写入者、Shadow 新模拟零写入，或当前模式在本场战斗生命周期内保持不变。
- 无法运行关键验证。此时可以完成安全实现，但不得宣称已通过；必须明确验证缺口和复现方法。
